## Q01: изменение обязательности в обе стороны

Предлагаемый компактный контракт, а не универсальный язык описания интерфейса:

```text
FieldRequirement = Required | Optional | Hidden
RegistrationPolicy = version + contactFieldRules
ContactFieldRule = fieldId + requirement + validationRules
```

По B06 phone nullable в User и Optional в исходной demo registration policy. Если заполнен — российский номер; имя на любом языке. Поля формы и проверка получают общий набор правил. Позднее источник может быть ответом API, конфигурацией или настройкой события.

- Required → Optional: ранее сохранённые телефоны остаются; пустое поле больше не блокирует новую регистрацию.
- Optional → Required: раньше выданные билеты действуют; при новой регистрации недостающий телефон надо дополнить. Не заставлять пользователя заново проходить вход и не создавать ошибку при открытии профиля.
- Hidden: не просить новое значение и не отправлять его автоматически без потребности контракта; существующее поле профиля не удалять. Видимость поля профиля и регистрационной формы — разные настройки.
- Новое базовое поле вводится одним типом/правилом и соответствующим form mapping. Произвольные вопросы организатора уже имеют отдельную схему, смешивать её с login/email identity не надо.
- Если правила изменились во время заполнения: обновить валидацию, сохранить совместимые ответы, объяснить недостающие поля. Backend повторно валидирует при отправке.
- Сохранить policy/form version в registration snapshot. Новая обязательность не аннулирует старые билеты; ретроактивные изменения требуют отдельного продуктового решения.

В contract tests добавить переключение Required ↔ Optional, Hidden без удаления профиля, смену правил во время формы и неизменность старых билетов. Гибкость не означает отдельный экран настроек этих правил: такого требования пока нет.

## Где остаётся риск правок

**Небольшие локальные изменения:** названия JSON-полей, endpoints, формат ошибок/дат, query/pagination, частота обновления, формат ручного кода. Это меняет DTO/репозитории/политики и некоторые проверки.

**Изменения сценариев:** сервер отказывается от гостевого билета, вводит телефон вместо email, требует подтверждать email до выдачи билета, меняет независимые связи на единую роль, добавляет платежи или офлайн-проход. Такое затронет auth/UI/domain; эти изменения нужно отдельно согласовать, а не маскировать сетевым адаптером. Поэтому B01–B06 полезно обсудить раньше, но готовый API для этого не нужен.

**Обязательные ответы до production:** протокол авторизации/продления, сроки кодов и подтверждения, ошибки и повторы API, удаление аккаунта, domain/App Links. Guest access исключён; распределение мест и серверные транзакции регистрации — ответственность backend. Android показывает результат операции.
