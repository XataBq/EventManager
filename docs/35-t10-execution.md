## Владение и порядок

- В каждый момент работает один агент в одной задаче. Не создавать субагентов, делегированные исследования или параллельное ревью.
- Реализационная задача меняет код, тесты и соответствующую текущую документацию в пределах одного M. Не начинать следующий зависимый M до технического принятия текущего.
- После реализации: значимые проверки → актуализация контекста → отчёт → фиксация проверяемого состояния → REVIEW_PENDING. Незавершённую передачу обозначать WIP_HANDOFF; она не закрывает критерии этапа.
- Ревью проводить отдельной последовательной задачей через [android-code-review](../.agents/skills/android-code-review/SKILL.md). Для независимой проверки предпочтителен новый самостоятельный агент/чат, запускаемый пользователем, без дочерних агентов. Во время ревью исходники только для чтения, изменяется только CODE_REVIEW.md с сохранением прежних записей. Самопроверка исполнителя не называется независимым ревью.
- Ревью уже входит в разрешённый цикл T10. Поздние продуктовые решения 08/34 имеют приоритет над ранними demo-правилами в скилле. Исправления — отдельный последовательный проход реализации, затем повторное ревью.
- Переходы: IN_PROGRESS → REVIEW_PENDING → TECH_ACCEPTED. При передаче незавершённого состояния: WIP_HANDOFF → IN_PROGRESS после запуска продолжения. P0–P2 закрывать исправлением и повторным ревью; P3 разбирать явно. Ручные H-проверки не отмечать за человека.
- Проверять diff, значимые тестовые артефакты и область своих изменений. Слова «тесты прошли» без команды/результатов не являются evidence. Старые или фильтрованные прогоны не заменяют проверку текущего состояния.
- Внешнюю недоступность фиксировать конкретно; skipped не считать passed. Спорное продуктовое решение уточнять до зависимых правок.
- Не добавлять в коммит всё грязное дерево автоматически. Сохранять исходные пользовательские правки, явно перечислять включённый контекст. Push только по поручению пользователя. 15 ноября push текущего снимка разрешён; это не постоянное разрешение на будущие push.

## Формат отчёта исполнителя

Для каждого M — отдельный `docs/validation/t10-mNN-implementation.md`:

1. **STATUS**: IMPLEMENTED/REVIEW_PENDING либо конкретно незавершённая часть; дата, M, base commit, проверяемый commit или манифест путей+SHA-256 рабочего состояния.
2. **SCOPE**: изменённые файлы, сохранённые исходные dirty изменения, baseline-копия; что явно не входило в этап.
3. **REQUIREMENTS**: таблица «критерий M → реализация/владелец → проверяющий тест или документ → результат». Не скрывать пропущенные критерии.
4. **ARCHITECTURE**: изменённые ports/state/DI/schema/ADR, точки commit/отмены/cleanup; ссылки на обновлённые текущие страницы.
5. **CHECKS**: точная команда, exit code, число тестов и путь XML/log, build/APK hash при выдаче. Список NOT_RUN с причинами отдельно; прежние результаты обозначать как прежние.
6. **RISKS**: подтверждённые ограничения, зависимости от API и незакрытые вопросы. Секретов/PII в отчёте нет.
7. **HANDOFF**: фактическое поведение, действующие ADR, удалённые старые пути, последняя область ревью, следующий M; что следующему агенту запрещено предполагать.

Итог пользователю и следующему самостоятельному агенту — краткая выжимка этих полей со ссылкой на полный отчёт. Если проверки ещё выполняются, указать это, не ставить итоговый успех.

## Формат отчёта ревьюера

CODE_REVIEW.md: дата, M, base/target commit или точный манифест, находки P0–P3 с путём/строкой/условием/последствием/доказательством, вопросы отдельно, команды и ограничения, состояние ручной приёмки. При исправлении — связь с прежней находкой и доказательство её устранения.

Итог отдельной задачи ревью: **VERDICT** (NO_CONFIRMED_FINDINGS / CHANGES_REQUIRED / INCOMPLETE_EVIDENCE), **SCOPE**, **FINDINGS**, **CHECKS**, **NOT_RUN**, **REPORT**. Отсутствие найденного дефекта не означает полного покрытия или готовности production.
