# T10: управление исполнением и отчёты агентов

13 ноября 2026 пользователь разрешил самостоятельное последовательное выполнение M00–M09 из [плана](34-api-migration-plan.md), использование субагентов для реализации и ревью, без команды на каждый этап. Ручная проверка только в конце. Это разрешение отменяет прежнее ожидание команды на запуск, но не означает приёмку ещё не выполненной работы.

## Владение и порядок

- Главный агент назначает одного исполнителя этапа, проверяет его evidence и только затем отдельного ревьюера. Исходники не меняются параллельно ревью. Независимое исследование следующего этапа допускается только read-only.
- Исполнитель меняет код, тесты и затронутую текущую документацию; ревьюер по [android-code-review](../.agents/skills/android-code-review/SKILL.md) меняет только CODE_REVIEW.md и сохраняет его предыдущие записи.
- Ревью — явно запрошенная пользователем часть этого цикла. Поздние продуктовые решения в 08/34 имеют приоритет над заменённым запретом autoaccount/verified-only в ранних инструкциях скилла.
- После отчёта главный агент проверяет diff, значимые тестовые артефакты и отсутствие посторонних изменений. Слова «тесты прошли» без команд/результатов не являются evidence. Ошибки возвращаются исполнителю; ревьюер не исправляет исходники.
- Переходы: IN_PROGRESS → REVIEW_PENDING → TECH_ACCEPTED. P0–P2 закрываются исправлением и повторным ревью, P3 разбираются явно. Ручная приёмка не требуется для следующего M и не отмечается агентами.
- При внешней недоступности фиксировать конкретное ограничение, выполнять независимые проверки/задачи и не выдавать skipped за passed. Для решения, меняющего продукт, запросить уточнение, не останавливая независимую работу.
- Нельзя автоматически включать в коммит всё изначально грязное дерево. Перед записью сохранять baseline затронутых файлов, фиксировать список своих файлов и точную область diff. Push без команды не выполнять.

## Формат отчёта исполнителя

Для каждого M — отдельный `docs/validation/t10-mNN-implementation.md`:

1. **STATUS**: IMPLEMENTED/REVIEW_PENDING либо конкретно незавершённая часть; дата, M, base commit, проверяемый commit или манифест путей+SHA-256 рабочего состояния.
2. **SCOPE**: изменённые файлы, сохранённые исходные dirty изменения, baseline-копия; что явно не входило в этап.
3. **REQUIREMENTS**: таблица «критерий M → реализация/владелец → проверяющий тест или документ → результат». Не скрывать пропущенные критерии.
4. **ARCHITECTURE**: изменённые ports/state/DI/schema/ADR, точки commit/отмены/cleanup; ссылки на обновлённые текущие страницы.
5. **CHECKS**: точная команда, exit code, число тестов и путь XML/log, build/APK hash при выдаче. Список NOT_RUN с причинами отдельно; прежние результаты обозначать как прежние.
6. **RISKS**: подтверждённые ограничения, зависимости от API и незакрытые вопросы. Секретов/PII в отчёте нет.
7. **HANDOFF**: фактическое поведение, действующие ADR, удалённые старые пути, последняя область ревью, следующий M; что следующему агенту запрещено предполагать.

Ответ главному агенту — краткая выжимка этих полей со ссылкой на полный отчёт. Если проверки ещё выполняются, указать это, не ставить итоговый успех.

## Формат отчёта ревьюера

CODE_REVIEW.md: дата, M, base/target commit или точный манифест, находки P0–P3 с путём/строкой/условием/последствием/доказательством, вопросы отдельно, команды и ограничения, состояние ручной приёмки. При исправлении — связь с прежней находкой и доказательство её устранения.

Ответ главному агенту: **VERDICT** (NO_CONFIRMED_FINDINGS / CHANGES_REQUIRED / INCOMPLETE_EVIDENCE), **SCOPE**, **FINDINGS**, **CHECKS**, **NOT_RUN**, **REPORT**. Отсутствие найденного дефекта не означает полного покрытия или готовности production.
