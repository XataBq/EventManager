# Правила реализации EventPass Android

Инженерная основа для T01 и следующих задач, 27 октября 2026. MVVM подтверждён в обсуждении. Остальные правила ниже — предлагаемые технические defaults для обратимых решений; они не утверждают несуществующий API или проверенную совместимость библиотек.

## MVVM без лишнего каркаса

Путь данных: действие пользователя → ViewModel → repository/use case → UiState → Compose. Compose отвечает за отображение и локальное поведение интерфейса. ViewModel координирует запросы и преобразование данных в состояние экрана. Репозиторий обеспечивает данные и операции; общая доменная политика определяет права на E.

| Часть | Соглашение |
|---|---|
| `FeatureRoute` composable | Получить ViewModel, собрать состояние с учётом lifecycle, связать callbacks с app navigation |
| `FeatureScreen` composable | Получает только UiState и callbacks; пригоден для previews, без Hilt/репозитория/NavController |
| `FeatureViewModel` | Constructor injection, публичный StateFlow<FeatureUiState>, закрытый MutableStateFlow; предметные методы действий |
| `FeatureUiState` | Неизменяемые данные для данного экрана, отдельно загрузка чтения и отправка изменения; не копия DTO |
| Use case | Только для переиспользуемой/сложной координации; не создавать обёртку на каждый getter |
| Domain | Чистый Kotlin, ID/модели/политики/порты; без Context, Resources, Parcelable, Retrofit DTO и Android ViewModel |
| Data/Platform | Конкретные адаптеры, преобразование transport/platform errors в domain outcomes |

Не создавать BaseViewModel, глобальный event bus, общий reducer/framework или огромный AppViewModel для всех экранов. Общие билеты/права живут в репозитории; маленькое состояние навигации/гостевого flow — у своего владельца. Hilt bindings находятся в app, чистые модели и политики не зависят от DI-фреймворка.

## Состояния, действия и результаты

Для каждого экрана описать до реализации: начальную загрузку, отображаемые данные, пустое состояние, ошибку, отправку, успех и необходимые ограничения доступа. Не заводить поля для состояний, которых у конкретного экрана нет. При обновлении не убирать уже видимые данные, если достаточно индикатора обновления/ошибки рядом с ними.

Долговечный результат, например выданный билет, хранится в состоянии, а не только в одноразовом Channel-событии. Нажатие Back/переключение вкладки обрабатывает навигационная оболочка. Переход после завершения запроса привязан к идентификатору результата и подтверждается обработкой, чтобы recomposition/возврат из background не создавали второй экран. Идентификатор не равен секрету билета. Нужен один маленький согласованный механизм на навигационной границе, а не собственная система effects для каждой фичи.

Отправка блокирует повторное нажатие до результата. Новый поисковый запрос заменяет прежний; устаревший ответ не затирает новый. После выхода/смены аккаунта старый ответ не обновляет данные новой сессии. Timeout не превращается в успех, Invalid QR или автоматическую повторную мутацию.

[Рекомендации Android по событиям](https://developer.android.com/topic/architecture/ui-layer/events) служат основанием различать UI-действие, бизнес-операцию и отображаемое состояние результата. Конкретные имена классов выше — решение проекта.

## Владелец гостевого QR

Предложение: GuestTicketFlowStateHolder/ViewModel в app, привязанный к записи гостевого flow и его SavedStateRegistryOwner. Activity не владеет бессрочным списком гостевых билетов. В Navigation 3 T01 сначала доказывает сохранение entry state и ViewModel ownership; конкретный API wiring фиксируется после выбора версии.

| Событие | Ожидаемое состояние |
|---|---|
| Успешный guest submit | Snapshot записан в state owner до показа QR; второй submit не запускается для восстановления картинки |
| Открыть fullscreen QR и вернуться | Тот же snapshot у общего владельца flow, без копирования в отдельный постоянный cache |
| Открыть вход/регистрацию поверх flow и Back | Если исходная запись осталась в стеке — QR доступен; ответы прежней анкеты отдельно не восстанавливаются |
| Пересоздание Activity / восстановление той же задачи системой | Восстановить минимальные поля snapshot из saved state; Bitmap заново построить из payload |
| Нажать явное закрытие flow / удалить исходную entry | Очистить snapshot и вложенные QR entries |
| Завершить задачу приложения и запустить новую | Гостевого билета нет; письмо/регистрация аккаунта и вход |
| Открыть ссылку с ticketId без snapshot/сессии | Не выдавать гостевой билет по ID; предложить вход или письмо |

Saved state хранит компактные сериализуемые значения, не изображения/файлы/полный API response. Отдельный DataStore/Room guest cache запрещён. Сохранённый back stack сам по себе не доказывает сохранение payload ViewModel: проверяется вместе с state owner. Системное уничтожение процесса отличается от явного закрытия пользователем — это поведение описано в [Android UI state](https://developer.android.com/topic/libraries/architecture/saving-states) и [Navigation 3 state](https://developer.android.com/guide/navigation/navigation-3/save-state).

## Репозитории, ошибки и корутины

- Чтение изменяемых данных — Flow; единичная команда — suspend с типизированным исходом. Не возвращать все ошибки как null/false или текст сервера.
- Ожидаемые ошибки API/валидации — domain outcomes; Android string resources выбираются в UI mapping. Domain не содержит `R.string` и не знает русский текст.
- Разные guest/auth операции имеют разные допустимые успешные результаты. Гость получает только snapshot из своего успешного submit; повторная/существующая регистрация не открывает произвольный ticketId.
- Не проглатывать CancellationException общим catch или runCatching; отменённый запрос не показывать как обычную сетевую ошибку. Ожидаемые transport errors преобразовывать в data-адаптере; неизвестные ошибки не скрывать бесшумно.
- Без GlobalScope и сетевой/дисковой работы в composable. Dispatchers/Clock инъектировать там, где это нужно для работы и тестирования; не добавлять withContext на каждом слое механически.
- Автоматический retry команд регистрации/check-in не вводить до соответствующего API-контракта. Текущий минимум — одна отправка, loading и явный исход; серверное распределение мест не реализуем.
- Не нормализовать email правилами конкретного почтового провайдера. Fake использует явно заданное совпадение тестовых email; реальный список билетов выдаёт backend после входа.

## Правила зависимостей и сборки

Пять стартовых модулей из 02 — предложенная структура. В T01 можно создать только минимальные файлы/один экран для проверки связей; не заполнять модули всеми будущими интерфейсами сразу. Platform APIs не протекают в domain; feature-пакеты общаются через ID/контракты, а не чужие ViewModel.

К T01 должны появиться wrapper, единый version catalog, `.gitignore` для local.properties/SDK paths/build outputs/ключей, локальное воспроизводимое описание сборки. Код и документацию версионировать в Git до первого завершённого этапа; удалённый репозиторий/публикация не требуются для старта. Не менять global Git/Java/Gradle settings ради одной сборки.

Все версии фиксируются без `+`, snapshot и случайного alpha; отступление документируется. Числа из 09 — ориентиры на дату исследования, не готовый lockfile. В README после реальной проверки записать сочетание Studio/JDK/Gradle/AGP/Kotlin/Compose/Hilt/KSP/navigation, команды и результат. Сначала assemble + DI/navigation smoke, затем распространение шаблона по фичам.

Начальная рабочая сборка — demoDebug. Demo явно помечено; реальная release/API-конфигурация не должна случайно использовать fake/debug outbox. Как именно ограничить варианты сборки, выбрать и проверить в T01. Не создавать пустую сетевую реализацию, которая сообщает успех.

## Минимальное качество изменений

Kotlin — официальное форматирование IDE как исходный default; один выбранный форматтер можно добавить после каркаса, не ставить несколько пересекающихся анализаторов. Android lint + релевантные unit tests обязательны для затронутого кода. Числовой порог покрытия сейчас не вводить: важнее сценарии из 07.

Пока CI-хост не выбран, проверочные команды воспроизводятся локально. До подключения нескольких разработчиков/первого PR перенести тот же набор в выбранный CI: assemble demoDebug, lint, JVM unit tests, сохранение диагностик. Device/UI-проверки запускать отдельно по необходимости, а не на каждом маленьком изменении. Не создавать workflow для выдуманного GitHub/GitLab-репозитория.

Тексты — string resources, числа/даты — форматирование UI с timezone события. Не логировать пароли, QR payload, reset codes и полные анкеты. Для диагностики достаточно имени операции, безопасного ID, кода исхода и duration; внешний crash/analytics сервис автоматически не подключать.

## Когда задача готова к началу и завершению

Перед началом задачи (Definition of Ready): известны актуальный сценарий, её границы, источник дизайна/состояния, данные fake, наблюдаемый результат и проверки. Неизвестный backend-механизм имеет временный адаптер, а не молчаливое продуктовое предположение. Если нужен только каркас, не требовать описать заранее все будущие экраны.

Перед завершением кодовой части (Definition of Done):

1. Выполнен сценарий в согласованном объёме, без лишних MAX-функций.
2. Проходит сборка и относящиеся к изменению проверки; точные команды/результаты записаны.
3. Нет незавершённых заглушек, выдающих ложный успех; реальные ограничения названы.
4. Есть сборка/seed/шаги для человека, если нужна ручная приёмка.
5. Основные документы и статус задачи обновлены, посторонние изменения сохранены.

READY_FOR_HUMAN означает «кодовая часть проверена, ручная приёмка ещё нет». DONE — после нужного H-gate. Независимая работа может продолжаться до ответа человека; запрещено отмечать H-проверки от его имени.

## Первый практический шаг T01

Минимальная доказанная основа: три корневых вкладки, один вложенный экран, одна Hilt ViewModel с UiState и минимальный demo repository. Проверить Back, отсутствие дублей, entry ownership и восстановление состояния. Выдать APK/команды. После этого T02/T03 развивают данные и UI-kit; не строить весь fake backend до проверки первого вертикального сценария.

## Минимальная acceptance-матрица первого пользовательского среза

Это добавление к S/A/M-реестрам из 05/07, не новая система идентификаторов. Для следующей фичи достаточно аналогичной компактной таблицы в её задаче.

| Поверхность | Вход / действие | Наблюдаемый результат |
|---|---|---|
| EventDetails | Loading → public E | Контент и доступность регистрации; Unknown не трактуется как Unlimited |
| EventDetails | Ошибка / 404 / closed / started / full | Различимое состояние; нет отправки закрытой формы; повтор чтения где уместен |
| Анкета | Пустое имя / optional phone / другие письменности | Предметная ошибка поля или допустимая отправка; заполненность consent учитывается |
| Submit | Двойное нажатие / задержка | Одна клиентская операция и loading, без ложного успеха |
| Submit | CapacityReached / Network / RequiresLogin | Соответствующий UI; нет автоматического retry/сохранения анкеты при login |
| GuestTicketReceipt | Новый успешный snapshot | QR виден, User не создан, другой билет/кабинет недоступен |
| Guest flow | Fullscreen/Back, recreation, close | Тот же snapshot до закрытия; после удаления flow новый запуск его не читает |
| Demo | Новый seed / outbox | Воспроизводимый сценарий, имитация письма обозначена; реальная рассылка не выполняется |
