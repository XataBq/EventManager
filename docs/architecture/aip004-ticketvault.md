# AIP-004 · TicketVault в EventPass

19 ноября 2026. Технический MVP проверяет, можно ли превратить PDF разных поставщиков в единую читаемую карточку и не перепутать входные коды. Продуктовый источник — [AIP-004, Ideas!A5:P5](https://docs.google.com/spreadsheets/d/124WUot8tXNh3A-XtUmnsXdvHIOEq9WlESxjv9E1r9dY/edit#gid=0&range=A5:P5).

## Что работает в MVP

В меню «+» третье действие открывает системный выбор нескольких файлов. Билеты из PDF также доступны отдельным входом из «Моих билетов». Каждая страница становится кандидатом на один билет. Пользователь сверяет найденные значения с оригиналом, может отредактировать предложенные поля, выбрать код, сохранить страницу либо пропустить её. Карточки сохраняются локально и открываются без запросов в API внутри доступной сессии EventPass. Для холодного запуска в режиме восстановления сессии доступ в профиль и навигация зависят от существующего auth gate.

Группировка использует подтверждённые название, дату, время и площадку. Сравнение нормализует регистр и пробелы. При отсутствии даты, времени или площадки объединение ограничено одним исходным PDF. Внутри группы можно переключать отдельные билеты. Дубликат определяется по SHA-256 полного файла и номеру страницы. Изменённая выгрузка того же билета может иметь другой хэш и считается отдельным источником.

Функция доступна в сборке remoteDebug, работающей с обычным API EventPass. Production release исключает импорт и библиотеку PDFBox. Импортированные карточки образуют локальный тип ImportedTicket. Регистрация, список выданных EventPass билетов, их статусы, серверная валидация и check-in используют свои прежние модели.

## Откуда берутся поля и код

| Шаг | Что делает MVP | Что видит пользователь |
|---|---|---|
| Выбор и изоляция | SAF даёт URI на чтение. Во временный файл копируется до 12 МиБ, проверяется сигнатура PDF и вычисляется хэш. До 5 файлов за импорт, до 8 страниц на файл | Понятная ошибка для нечитаемого, защищённого PDF, повторной загрузки или превышения лимита. Ошибка одного файла оставляет остальные страницы доступными для проверки |
| Текст | PDFBox-Android получает текст отдельно для каждой страницы в позиционном порядке. TicketFieldRecognition ищет русские и английские подписи и нормализует дату и время. Уникальная дата/время без подписи — только подсказка. Конфликтующие значения оставляют поле пустым | Пример: «Сектор: B · Ряд: 7 · Место: 15» превращается в три поля. У предложения показывается фрагмент исходной строки. Заголовок без узнаваемой подписи можно заполнить вручную |
| Дополнительные поля | Узнаваемые подписи, включая тариф, тип билета, уровень и дверь, попадают отдельно как пары label/value. Берутся однозначные значения, размер полей ограничен | Дополнительная строка показывается только когда найдена и подтверждена. Значение можно исправить или стереть |
| Коды | PdfRenderer растеризует страницу с ограниченным размером. ZXing ищет QR и распространённые 1D/2D коды. Кандидаты привязаны к странице. Если их несколько, приложение просит выбрать один либо оставить код только в оригинале | Можно сверить предлагаемый код с исходной страницей. Для скана без текста код всё равно может распознаться, а текстовые поля заполняются вручную |
| Подтверждение и запись | Сохраняются только подтверждённые поля, выбранный тип/текст кода и оригинал. Данные и оригиналы разделены по аккаунтам в noBackupFilesDir, запись через AtomicFile. Оригинал один на PDF и удаляется после удаления его последней карточки | Карточка и оригинал доступны в локальном хранилище. Можно удалить импортированный билет |

Текст, PDF, имена и payload кодов не отправляются на сервер импорта или модели. Системный SAF может читать файл у выбранного облачного провайдера. Интеграция с удалением аккаунта и шифрование отдельно от защиты Android оставлены для продуктового этапа. Данные других аккаунтов недоступны в интерфейсе текущей сессии.

Для minSdk 28 используется PDFBox-Android как источник текста. Платформенный PdfRenderer используется для страниц и изображения кода. Его собственное извлечение текста появилось в API 35. [PDFBox-Android](https://github.com/TomRoush/PdfBox-Android) · [Android PdfRenderer.Page](https://developer.android.com/reference/android/graphics/pdf/PdfRenderer.Page).

## Как строится адаптивный билет

Компоненты Compose читают семантический результат, а оригинальный PDF открывается отдельным просмотрщиком. Название растёт по высоте. Дата, время, площадка и длинный адрес занимают обычные строки с переносом. Сектор, ряд, место и вход раскладываются слева направо и переносятся в следующий ряд по доступной ширине. ФИО, номер, цена и дополнительные реквизиты выводятся только если заполнены. У карточки нет фиксированной высоты.

| PDF | Карточка |
|---|---|
| Концерт с площадкой, сектором, рядом, местом и тарифом | Заголовок и адрес, сетка мест, строка тарифа, действие показа QR |
| Билет со свободной рассадкой | Заголовок, дата, площадка, исходный PDF и код при наличии |
| Скан без текстового слоя | Подтверждённые вручную поля, исходная страница и найденный код при наличии |

Полноэкранный режим сохраняет распознанную символогию при повторной отрисовке и позволяет перейти к оригиналу. Автоматическая проверка оценивает равенство декодированного текста на синтетических примерах. Бинарные коды, динамические коды, физическое считывание на турникете и подлинность билета в этом срезе не подтверждаются. Несколько билетов на одной странице требуют сегментации макета и отдельной привязки кода к каждому блоку.

## Выбор технологии после проверки

| Подход | Когда использовать | Как проверять |
|---|---|---|
| Локальные правила и шаблоны поставщика | Первая линия для PDF с текстом, знакомыми форматами и повторяющимися макетами | Доля верных полей по оператору. Отдельно измерять пропуски и неверные автоподстановки |
| OCR в отдельном шаге | Скан или PDF без читаемого текстового слоя | Проверка кириллицы, наклонов и плохой печати. Измерять качество OCR отдельно от ошибок сопоставления полей |
| LLM со схемой JSON | Текст доступен, но поставщики используют разные подписи и нестандартное расположение | Передавать минимальные фрагменты с ID страницы и строки. Модель обязана вернуть поле, значение, ссылку на доказательство и null при неопределённости. Валидатор отвергает значения, отсутствующие в источнике, проверяет дату, отделяет дату заказа от даты события. Чтение и привязка QR/штрихкода остаются локальными |

Облачный вариант требует отдельного согласия, защищённого прокси, политики минимизации ФИО и реквизитов, измерений задержки и стоимости. LLM в MVP не подключена. Она полезна для поиска кандидатов, но не решает привязку нескольких штрихкодов по координатам, недоступность PDF или проверку подлинности. На следующем этапе имеет смысл разложить страницы на текстовые блоки с координатами, использовать координаты найденных кодов и проверять принадлежность к той же карточке. При неоднозначности нужен отказ от подстановки и показ оригинала.

Практический следующий прогон — 50–100 обезличенных билетов разных операторов из AIP-004. Для каждого записать точное название, дату, время, площадку, сектор/ряд/место и ожидаемый payload с номером страницы. Сравнивать два прогона на одной выборке: правила и правила с семантической подстановкой. Метрики — точность автоподстановки и покрытие по каждому полю, доля полностью верных билетов, неверная привязка кода, время обработки и доля ручных исправлений. Включить пачки соседних мест, билеты без мест, повторный импорт, билет с датой покупки, два QR и страницы, где один из кодов мелкий. Ошибочная автоматическая привязка кода — отдельный блокирующий критерий перед включением в release.

## 20 ноября. Импорт реальных PDF и управление карточками

Чтение происходит на устройстве. PDFBox-Android извлекает текст и границы слов. Общие правила связывают значения с соседними подписями или заголовками колонок. Они также распознают даты с названиями месяцев. PdfRenderer отрисовывает страницу или участок, а ZXing считывает из изображения QR или штрихкод. Для страницы с единственным напечатанным 13-значным номером повторная попытка ищет EAN‑13 рядом с номером и принимает результат участка при точном совпадении. Напечатанный номер сам по себе не становится штрихкодом.

При пустом текстовом слое либо при группе чисел с пропущенными подписями включается локальный OCR Tesseract через tess-two 9.1.0, с русской и английской моделями 3.04.00. При наличии группы чисел OCR получает небольшой участок, найденный по положению чисел. Движок имеет один выделенный рабочий поток и владеет копией изображения. Импорт ждёт результат OCR не дольше пяти секунд на страницу. Если OCR занят или не успел, карточка получает результаты текстового слоя и декодирования штрихкода. Уже запущенная нативная операция может завершиться позже, а до её завершения конкурирующий OCR не запускается. Содержимое PDF, кодов и OCR не отправляется внешнему сервису.

В списке корзина включает режим выбора, в котором карточки отмечаются галочками. Крестик или системный Back сбрасывают выбор. ViewModel хранит выбранные локальные ID, после подтверждения удаляет только их и перечитывает оставшиеся записи. Общий PDF сохраняется, пока на него ссылается хотя бы одна карточка. В деталях код отображается при открытии и разворачивается по тапу. Изменение яркости ограничено окном развёрнутого кода. Повторное распознавание сохранённой карточки использует её исходную страницу и применяет изменения только после сохранения формы.

На AVD API 28 исходная сборка code32 выдала три страницы ЦСКА примерно через 252 с. Code33 подготовил предложения по этим же страницам примерно за 8,5 с и во всех трёх нашёл название, дату, время, сектор, ряд, место и EAN‑13. На шести страницах гонок нашлись название, дата, время, площадка, адрес, ряд, место и коды. Сектор гонок требует ручной проверки. В том же прогоне прошли проверки чтения кадров, локального сохранения и повторного распознавания без дубля, синтетических файлов и адаптивной карточки. Итог **4 из 4 тестов**. Частные PDF и значения кодов не добавлены в репозиторий.

### Code34. Отдельный поиск линейного кода, повторный разбор и свайпы

На четвёртой странице PDF гонок обычный поиск нашёл QR, но пропустил Code 128. Теперь PDF-импорт проверяет линейные коды отдельно. Кандидаты из читаемых печатных номеров задают небольшие участки для повторного рендера и проверки точного совпадения декодированного значения. Положение участков вычисляется для конкретной страницы. При повторном распознавании поиск линейных кодов может использовать более чёткий рендер. Результаты QR и линейного поиска показываются как разные варианты при подтверждении билета.

«Распознать страницу заново» перечитывает текущий черновик по исходному файлу и номеру страницы. ViewModel сохраняет порядок очереди, введённые поля и явный выбор кода, если он остаётся доступным. Пустые поля могут получить новые предложения. Свайпы в деталях и развёрнутом коде меняют одну и ту же выбранную карточку внутри группы. Если для соседней карточки код не выбран, полноэкранный режим предлагает открыть оригинал текущего PDF.

У первого OCR в новом процессе есть до восьми секунд на запуск и распознавание. Последующие вызовы ограничены пятью секундами. Это компенсирует загрузку моделей при холодном старте.

Финальный прогон API 28 прошёл **5 из 5 тестов**. Все шесть страниц гонок вернули QR и Code 128, отдельная проверка четвёртой страницы повторила результат. Все три страницы ЦСКА вернули EAN‑13, сектор, ряд и место. Тест прошёл свайп в карточке, свайп в открытом коде и возврат к тому же билету после закрытия окна. Сборка code34 установлена и запущена на Redmi. APK лежит в `artifacts/apk/EventPass-0.10.17-AIP004-code34.apk`.

### Code35. Анимация перелистывания

Детали билета и развёрнутый код используют один горизонтальный переход Compose длительностью 260 мс. Направление следует порядку билетов в группе. Код, номер карточки и её реквизиты анимируются вместе по ID билета. В развёрнутом окне также видны сектор, ряд и место, когда они сохранены. Кнопки закрытия и открытия оригинала закреплены. Оба существующих UI-теста PDF прошли на Android 9. [AnimatedContent в Compose](https://developer.android.com/develop/ui/compose/animation/composables-modifiers#animatedcontent).
