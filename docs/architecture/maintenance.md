# Как сопровождать архитектуру

Эти правила относятся к текущей документации [00](../00-documentation-map.md), [02](../02-architecture.md), [03](../03-navigation.md), [05](../05-data-contracts.md) и картам в этой папке. Исторические отчёты и архивы не являются второй действующей спецификацией.

## Definition of Ready для изменения

До реализации назвать:

1. Изменяемую функцию и владельца ответственности из [карты](responsibilities.md).
2. Допустимые зависимости, текущий port/outcome и доступ на eventId/session.
3. Владельца state, что сохраняется и когда очищается — [lifecycle](state-ownership.md).
4. Если есть мутация: точку commit, update Flow, отмену/late result/finally.
5. Изменение snapshot и миграцию, если persisted данные меняются.
6. Проверку наблюдаемого инварианта и человеческую приёмку, если нужна.

Не требовать продуктовых решений для каждого обратимого UI-параметра. Неизвестный API обозначить как временный adapter/default с конкретной точкой согласования. Если код ещё не прочитан, описание считается гипотезой, а не установленной архитектурой.

## Что обновлять вместе с кодом

| Триггер | Обязательная документация |
|---|---|
| Новая/перенесённая ответственность, module/source-set dependency | 02 и responsibilities; проверить Gradle declarations |
| Route/owner/Back/Logout/process restore | 03 и state-ownership; проверить ключи и реальный host wiring |
| Repository API/outcome/guard | 05; operations/invariants для затронутого пути |
| Persisted поле/schema/asset | 05, state-ownership и migration evidence |
| Новый бизнес-инвариант/регрессия | invariants → test/source; продукт 01/решение 08 при изменении правила |
| Изменение принятого архитектурного решения | Новый ADR/дополнение в 08 с основанием; текущие страницы переписать по итоговому поведению |
| Завершение задачи/ручная приёмка | 06 и отчёт этапа; не менять gate по выводу автоматического теста |

Текущий документ описывает **одну** версию поведения. Не добавлять над ним очередную хронологическую сводку с несовместимой старой спецификацией ниже. История — в отчёте/ADR/Git; старые крупные варианты при необходимости отдельным архивом. Ссылки на ранее отправленные отчёты сохраняются.

## Проверка документационного изменения

Из корня PowerShell:

```powershell
python scripts/verify-architecture-docs.py
git diff --check
```

Скрипт проверяет наличие локальных целей ссылок текущих архитектурных страниц, парность fenced blocks, сохранение реестров 18 mobile-frame и S01–S14, наличие основных правил и файлов-источников. Это структурная проверка, **не** Mermaid parser, не сравнение смысла с Kotlin и не полный поиск битых ссылок во всей истории проекта. Он не требует Android toolchain/интернета.

Дополнительно человек/агент читает diagram edges против кода: зависимость, владение и вызов — разные виды стрелок; подпись должна сообщать вид схемы. После изменения схемы проверить Mermaid rendering доступным viewer, если он есть; при отсутствии parser/viewer явно назвать этот предел. Не устанавливать инфраструктуру screenshot tests ради Markdown.

При изменении только документации Android assemble/tests не нужны. При изменении кода выполняются релевантные проверки из 14 и задачи. Версии APK/числа тестов/hash не копировать в каждую схему — ссылка на актуальный отчёт достаточно.
