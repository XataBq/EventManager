## 2. Обязательные продуктовые правила

1. Один аккаунт без поля `role`. Независимые отношения: владелец события, grant сканирования, регистрация участника. Они могут пересекаться даже на одном событии. Создать событие может любой вошедший подтверждённый аккаунт. Владельцу/волонтёру билет автоматически не выдаётся.
2. Гостевая регистрация не создаёт аккаунт. Новая успешная заявка сразу возвращает QR и отправляет билет на почту. Подтверждение email не требуется, место уже занято. После закрытия гостевого flow нет API «найти все билеты по email» или свободного чтения по `ticketId`.
3. После отдельной регистрации аккаунта, подтверждения почты и **ручного входа** сервер отдаёт все билеты на подтверждённый email. Клиент не присваивает регистрации самому себе.
4. Подтверждение email не выдаёт сессию. Сброс пароля: email → код из письма → новый пароль → ручной вход. Предварительный verify email для начала сброса не нужен.
5. Имя на любом языке. Телефон optional, если указан — российский номер. Email профиля read-only. Имя, телефон и организация редактируются.
6. Ответы анкеты не сохраняются перед входом, не отправляются автоматически после него. Разрешён только безопасный возврат на исходное мероприятие. Черновики **редактора мероприятия** — отдельная функция, их сервер сохраняет.
7. После первой регистрации вопросы, варианты, порядок и обязательность вопросов фиксируются навсегда для этого события. Отмена всех билетов не снимает блокировку.
8. Регистрация закрывается вручную или при наступлении `startsAt`. Завершение — вручную или по `endsAt`; начало не означает завершение. Публичная страница после закрытия регистрации доступна.
9. `capacity=null` — без лимита; оставшихся мест `0` — нельзя регистрироваться. ACTIVE и USED занимают место, CANCELLED не занимает. Последнее место распределяет сервер; Android показывает результат.
10. Один неотменённый билет на нормализованный email и событие. ACTIVE можно отменить один раз, USED нельзя. После отмены можно зарегистрироваться заново при доступности; новый билет и новые credentials.
11. Только владелец и действующий волонтёр E проверяют билеты E. Волонтёру недоступны участники, экспорт, редактор и выдача прав. Отзыв grant сохраняет его личный билет и историю проходов.
12. Первый проход ACTIVE → USED. Повтор — ALREADY_USED с данными первого прохода; чужой/отменённый/неизвестный билет — INVALID без персональных данных. Ошибка сети не является INVALID или разрешением прохода. Офлайн-допуска нет.
13. Тексты пользовательских ошибок находятся в Android resources. Сервер возвращает машинные коды и параметры, не русский текст для прямого отображения.

## 3. Общие соглашения HTTP

База `/api/v1`, HTTPS. `https://api.eventpass.example` в OpenAPI — заведомо пример, не реальный домен. Отдельные staging и production с отдельными пользователями, ключами и почтовыми настройками.

JSON UTF-8, имена camelCase, статусы UPPER_SNAKE_CASE. Успех без общей обёртки `data`, структура зависит от операции. `204` без тела. В JSON-схемах явно указано, какие поля обязательны и допускают `null`. Для PUT передаётся **полная** редактируемая структура; `null` очищает nullable-поле, пропущенное обязательное поле — ошибка. Клиент игнорирует новые неизвестные поля ответа. Сервер отклоняет неизвестные поля команды: нельзя незаметно принять `ownerId`, `userId`, `status`, `checkedAt` от клиента.

Все ID непрозрачные строки до 80 символов `[A-Za-z0-9_-]`; клиент не извлекает из них смысл. В новых черновиках `draftId` создаётся клиентом как UUID v4. `questionId`/`optionId` стабильные ID клиента; уникальность внутри формы/вопроса проверяет сервер. Массив задаёт порядок, отдельного `order` нет.

Время — RFC 3339, ответы в UTC с `Z`; принимаются даты с явным offset. `zoneId` отдельно, IANA (`Europe/Moscow` по умолчанию редактора). Сервер — источник текущего времени, отдаёт `Date` и `serverTime` в зависящих от времени чтениях. Граница закрытия: `now >= startsAt`, завершения: `now >= endsAt`. Если `endsAt=null`, автоматического завершения нет. Даты без offset не принимаются; Android разрешает неоднозначность DST до отправки.

`revision` — версия редактируемого объекта, `formVersion` — только схемы анкеты, `dashboard.revision` — изменения данных явки/списка. Это разные счётчики. `expectedRevision` защищает от затирания правок с другого устройства. Несовпадение → `409 REVISION_CONFLICT`, клиент перечитывает данные и предлагает повторить изменение; автоматического merge нет.

Списки: `limit=30`, максимум 100; `cursor` непрозрачен, связан с пользователем/фильтром/сортировкой, срок 15 минут. `nextCursor=null` — конец. Первый запрос фиксирует набор и порядок ID на момент `snapshotAt`; дальнейшие страницы не дублируют и не пропускают ID из этого набора. Поля записей могут отражать более новое состояние, новые записи появляются при обновлении первой страницы. Удалённые/недоступные записи пропускаются, права проверяются заново на каждой странице. Если реализация не может сохранить набор, возвращает `410 CURSOR_EXPIRED` с необходимостью начать заново, а не молча смешивает страницы. Стабильный tie-breaker — ID. Tickets: `createdAt DESC,id`; события: `startsAt ASC,id` для CURRENT, `startsAt DESC,id` для PAST; drafts: `updatedAt DESC,id`; volunteers: `grantedAt ASC,userId`. Attendees — параметр sort, при равенстве ID.

Для auth, QR, персональных данных и файлов: `Cache-Control: no-store`. Обложки — отдельные разрешённые публичные assets после публикации. Нельзя кэшировать персональные capabilities как общедоступную страницу. При неверном bearer публичный endpoint с optional auth отвечает 401, не понижает запрос молча до гостя.

`X-Request-Id` генерирует сервер и повторяет в ошибке. Это диагностический ID, не ключ идемпотентности. Не логировать пароли, bearer/refresh, reset/confirm-коды, QR/manual credentials, тела анкет, полный email и URL с секретами.

## 4. Вход, токены, хранение и проверка

### 4.1 Что уже реализовано и что предлагается

Сейчас Android работает с локальным `FakeAuthRepository`: сессия на 30 минут в памяти, без production access/refresh и без восстановления авторизации после нового процесса; confirm/reset challenge на 15 минут, повтор через 60 секунд. Это demo, его параметры не переносятся автоматически в сервер.

**Предложение для API:** собственная first-party email/password авторизация и два случайных opaque bearer-токена. Это не OAuth password grant, не полноценный OAuth/OIDC сервер. Если позже нужен внешний провайдер, согласовать отдельный Authorization Code + PKCE flow. JWT для мобильного MVP не требуется: с серверной таблицей сессий проще обеспечить немедленный logout/блокировку. Android всё равно не должен разбирать токен или проверять его подпись.

| Секрет / объект | Срок | Применение и проверка |
|---|---|---|
| Access token | 15 минут от выдачи | 32 случайных байта CSPRNG, base64url без padding; заголовок `Authorization: Bearer ...` |
| Refresh token | 30 дней без успешного refresh | Отдельные 32 случайных байта; только тело `/auth/refresh` или `/auth/sign-out`; ротация при каждом refresh |
| Семья сессии устройства | Максимум 90 дней от login | Refresh не продлевает абсолютный предел; после него ручной login |
| Email verification token | 24 часа | 32 случайных байта, одно назначение/аккаунт; отправляется только письмом |
| Код сброса | 10 минут | 6 случайных десятичных цифр, включая ведущие нули; максимум 5 неверных попыток на challenge |
| Reset grant | 5 минут после проверки кода | Отдельный 32-byte secret; только смена пароля; одноразовый |
| Deletion confirmation | 10 минут | Привязан к аккаунту, сессии и снимку последствий; дополнительно нужен текущий пароль |
| Ticket QR | Пока билет допустим | 32 случайных байта; не access-token; не истекает через 15 минут. Проверяются билет, событие и права сканера |
| Manual code | Тот же срок, что QR | Отдельный случайный 12-символьный код, одна регистрация; одинаковый эффект проверки |
| Document job/file | 24 часа | Всегда требуется bearer и актуальное право; ID задачи не является разрешением |

Сроки — проектные значения, а не требования Android или RFC. Если команда меняет их до первой интеграции, обновить OpenAPI/документ/contract tests вместе.

### 4.2 Login и каждый закрытый запрос

1. `POST /auth/sign-in`: email, password и device metadata. Email нормализуется по единой политике §5. Пароль не trim, не lowercase, не сохраняется клиентом.
2. Сервер находит аккаунт и сравнивает пароль с password hash. Неизвестный email и неверный пароль → одинаковые `401 INVALID_CREDENTIALS` и сопоставимое время обработки. Android показывает «Неверный пароль»/общую строку из ресурсов по принятому UX.
3. Только после правильного пароля проверяется emailVerified. Неподтверждённый → `403 EMAIL_UNVERIFIED`, токены не выдаются. Удалённый аккаунт не входит.
4. Успех создаёт отдельную семью сессии устройства, возвращает `SessionTokens` и профиль. Несколько устройств разрешены; login не выкидывает остальные устройства. `installationId` помогает диагностике, но его можно подделать, поэтому он не заменяет секрет.
5. На каждом закрытом запросе сервер хеширует access, находит token/session, проверяет expiry, отзыв, активность аккаунта и подтверждение email. Затем проверяет принадлежность объекта и право **на запрошенный eventId**. Права не берутся из переданного body или клиентских capabilities.
6. При изменяющей операции финальная проверка права выполняется перед фиксацией результата. Отзыв grant, зафиксированный до этой проверки, запрещает операцию. Уже завершённый проход отзыв не отменяет. Не нужен Android-механизм распределения мест или серверный mutex в клиенте.

Пароли сервера: Argon2id с солью на пользователя; исходный ориентир параметров не ниже 19 MiB, 2 прохода, parallelism 1, затем измерение нагрузки на реальном сервере. Не копировать demo password proof как production решение. Основание — [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Access/refresh/confirm/reset grant в БД хранятся как криптографические digest/HMAC, а не открытые строки. Для короткого reset-кода нужен keyed HMAC с серверным секретом и лимит попыток: простой SHA-256 шестизначного кода не защищает от перебора при утечке таблицы. Серверный secret/key управляется отдельно от БД. QR/manual дополнительно понадобятся для повторного показа и PDF: encrypted-at-rest оригинал + индекс HMAC для поиска, с ограничением доступа к ключу. Пароль таким способом не шифруется, только password hash.

### 4.3 Refresh и ошибки

Android отправляет refresh примерно за минуту до expiry access при необходимости запроса, либо после `401 ACCESS_EXPIRED`. Одновременно выполняется **один refresh на сессию**; остальные запросы ждут. Новый access/refresh сохраняются атомарно. Сам refresh не перехватывается тем же механизмом рекурсивно.

Сервер проверяет digest refresh, активность семьи, inactivity/absolute expiry, пользователя. При успехе старый refresh помечается использованным, выдаётся новая пара. `refreshExpiresAt=min(now+30 дней, absoluteExpiresAt)`. Новый access ограничен 15 минутами и абсолютным сроком сессии. Старые access этой семьи живут до своего expiry, если не отозвана сама семья.

Для потери ответа refresh используется тот же `Idempotency-Key`: 60 секунд сервер хранит зашифрованный результат ротации и возвращает **ту же** пару только на совпадающий старый refresh + key. Другой ключ со старым refresh или повтор после окна → `401 REFRESH_REUSED`, отзыв всей семьи и всех её access. Отозванная logout/reset/deletion семья не оживляется даже replay. Клиент держит pending refresh-key рядом с защищённым состоянием токенов до завершения, чтобы повтор после краткого сбоя не создавал ложный replay. Если ответ потерян дольше окна, безопасный исход — ручной login. Полное исключение этого случая не обещаем.

Повтор исходной бизнес-команды после обновления access допускается максимум один раз, с прежним idempotency key/body. `403 FORBIDDEN` не лечится refresh. `401 REFRESH_INVALID/EXPIRED/REUSED/SESSION_REVOKED` → очистка локальной сессии и вход. Timeout/503 refresh → ошибка связи/повтор, **не** удаление refresh и не ложный logout. Пока сессию нельзя проверить, закрытые операции не выполняются.

Ротация и обнаружение повторного refresh согласуются с принципами [RFC 9700, §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14); выбранные TTL и 60-секундное окно — наше предложение, не предписание RFC. При смене механизма backend должен сохранить понятный контракт logout/replay/отзыва.

### 4.4 Android storage и logout

Access держать в памяти. Refresh, sessionId и pending refresh operation хранить в приватном encrypted storage с ключом Android Keystore, исключённом из backup; не в SavedStateHandle, plain SharedPreferences, логе или navigation route. Пароль, код сброса, подтверждение — только память текущей операции. QR гостя — отдельное согласованное исключение: компактный snapshot в saved state текущего flow, без постоянного ticket cache.

После нового процесса: Unknown → прочитать защищённый refresh → refresh → профиль → Authenticated; отсутствие refresh → Guest. Сетевая ошибка восстановления не должна превращать пользователя в подтверждённого или удалять его действующий refresh. Навигационный `Session.expiresAt` нельзя напрямую считать expiry короткого access: refresh не должен каждые 15 минут уничтожать private stacks. Требуется адаптация SessionCoordinator/remote auth (§13).

Logout: `POST /auth/sign-out {refreshToken}` отзывает всю указанную семью и access; даже если refresh уже ротирован, он должен идентифицировать семью для отзыва. Неизвестный/просроченный/уже отозванный → 204. Android в любом случае очищает свою сессию и private UI. При отсутствии сети серверный отзыв **не подтверждён**: локальный выход успешен, удалённая сессия может жить до срока. Не показывать ложное «вышли на всех устройствах»; отдельного такого UI/метода в MVP нет.

Сброс пароля и удаление отзывают **все** сессии пользователя. Обычное обновление профиля не отзывает сессии.

### 4.5 Подтверждение и восстановление

Sign-up требует name/email/password/consent. Успех 201 создаёт неподтверждённый аккаунт и challenge, ставит письмо в очередь, сессию не создаёт. Занятый email → `409 EMAIL_TAKEN` (это допустимое согласованное раскрытие). Повтор отправки confirm — через 60 секунд, новый challenge отменяет старый. Нельзя менять пароль неподтверждённого аккаунта повторным sign-up.

Confirm: приложение получает challengeId/token из письма и отправляет POST. Открытие ссылки HTTP GET само ничего не подтверждает: почтовый link-scanner не должен поглотить секрет. Верный повтор уже использованного proof возвращает `ALREADY_VERIFIED`, но не сессию. Неверный/устаревший proof не раскрывает email аккаунта. После успеха пользователь входит вручную.

Reset-request и resend-confirm возвращают неотличимый 202 challenge даже для неизвестной почты (или уже подтверждённой при resend). Письмо отправляется только подходящему аккаунту. Код reset может быть запрошен и для неподтверждённого аккаунта. Проверка кода создаёт resetGrant, потребляет код. Смена пароля потребляет grant и отзывает сессии; не устанавливает `emailVerified=true` автоматически и не выполняет login. Такой аккаунт отдельно подтверждает email. Это явное предложение, закрывающее неописанный крайний случай.

Новые запросы кода инвалидируют старые коды и неиспользованные reset grants этого аккаунта. Повтор verify с тем же key 60 секунд возвращает тот же grant; новый key после потребления → CHALLENGE_CONSUMED. Для complete точно такой же key/body после успеха возвращает 204 в пределах 24 часов, без повторной смены пароля. 5 неверных кодов закрывают **challenge**, не весь аккаунт; следующий запрос ограничивается cooldown. Принципы одноразовых ограниченных кодов и одинаковых ответов сверены с [OWASP Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

## 5. Поля и централизованная валидация

| Поле | Предлагаемое правило |
|---|---|
| name | trim, 1–200 Unicode code points, без управляющих символов; допустимы любые письменности, дефисы, апострофы, одно слово |
| email | trim, максимум 254; одна серверная политика для login/signup/guest/grant/ticket matching. Предложение: case-insensitive весь адрес, IDNA домен; без удаления `+tag` и точек. Поддержку Unicode local-part определяет почтовый провайдер; для v1 ASCII local-part, international domain через IDNA. Это отличие от demo exact-match, требует сверки до миграции |
| password | 8–128 code points, без управляющих символов; не нормализовать и не обрезать, не требовать конкретного алфавита/наборов символов; не принимать распространённые скомпрометированные значения |
| phone | null или канонический `+7` + 10 цифр. Android принимает удобный ввод `8 (...)`/`+7 (...)`, нормализует до отправки. Это синтаксическая проверка российского формата, не подтверждение владельца номера; SMS не требуется |
| organization | null или trim 1–200; не отдельная системная роль и не ответ анкеты |
| title / venue / description | до 200 / 1000 / 10 000; plain text; title/venue непустые при публикации |
| sections | до 50, title/time до 1000; подпись времени программы не влияет на lifecycle |
| questions | до 100; title до 500; TEXT / CHECKBOX / SINGLE_CHOICE; ID стабильный, уникальный |
| options | до 100 на single choice, минимум 1 при публикации; title до 300, непустые уникальные после trim/casefold |
| answers | до 100, questionId не повторяется; TEXT до 4000; обязательный текст непустой, обязательный checkbox=true, choice из текущих options |
| cover | optional, JPEG/PNG, 1–5 242 880 байт; исходное соотношение сторон может отличаться, UI показывает crop 16:9 |

Сервер окончательно валидирует независимо от Android. Неизвестные questionId/options, неверный тип ответа и дубли → 422 fieldErrors. Пропуск необязательного вопроса допустим. Optional checkbox=false — настоящий ответ. Пустая строка телефона приводится Android к null. `phoneRequirement=HIDDEN` запрещает новые телефонные данные в заявке, но не стирает старые ответы; REQUIRED требует непустого phone. В MVP config=OPTIONAL, отдельного owner-toggle нет. Если политика меняется, обновляется форма/версия; после первой регистрации политика конкретного E тоже фиксируется — **предлагаемое** упрощение, чтобы не менять условия анкеты задним числом.

Версии terms/privacy приходят из `/config` и PublicEvent. Сервер сохраняет версии и своё время согласия. Неверная версия → 409 POLICY_CHANGED, перечитать и получить новое согласие. Реальные тексты/URL предоставляет команда, Android их не выдумывает.

## 6. Мероприятия, черновики и обложки

`GET /events/{eventId}` — общая публичная страница, анкета, ограничения, serverTime, capabilities. Без bearer — без персональных данных; `ownTicketId=null`. С bearer — собственная связь и права. Draft/удалённый объект → 404, без раскрытия его содержимого. Отдельный owner editor endpoint возвращает editableFields.

`GET /me/events?relation=OWNED|VOLUNTEER&period=CURRENT|PAST` обслуживает общий экран. Независимые запросы вкладок не превращают пользователя в «роль». Завершённые волонтёрские скрыты (PAST возвращает пустой список), свои завершённые доступны. STARTED с `endsAt=null` остаётся текущим до ручного завершения. Черновики отдельным `/me/event-drafts`.

`PUT /event-drafts/{uuid}` сохраняет полный EventFields. Первый save: expectedRevision=null; последующие — конкретная версия. Неполные значения разрешены, но ограничения размеров, ID, типы и принадлежность обложки проверяются всегда. Черновики сохраняются на сервере, доступны на другом устройстве. UI не обязан autosave. Удаление черновика отдельным действием в текущем MVP не задано, поэтому ручка удаления не добавлена.

Публикация — POST publication: валидные title/venue/startsAt в будущем, endsAt позже startsAt, timezone, capacity>=0, корректная анкета. Возвращает eventId/publicUrl; сохраняет связь draft→event. Повтор публикации того же draft всегда возвращает тот же E. Черновик после публикации исчезает из списка, владелец может получить publication receipt; изменять его как draft уже нельзя.

Редактирование E требует expectedRevision и expectedFormVersion. До первой регистрации можно менять анкету с увеличением formVersion. После неё — QUESTIONS_LOCKED; title/venue/description/sections/cover/capacity можно, если событие ещё не закончено. После startsAt даты начала/конца/zone менять нельзя. capacity ниже ACTIVE+USED отклоняется. Finished/Cancelled терминальны для редактирования. Эти ограничения дат и metadata уже являются demo defaults; предлагается оставить их в API.

`registration-closure` выставляет registrationOpen=false. Уже закрытое E возвращается без дополнительного эффекта; если целевое состояние не достигнуто, проверяется revision. Отдельного reopen нет в текущем плане. `completion` завершает E и закрывает регистрацию; повтор завершённого даёт тот же результат. Даже без cron читатель/валидатор вычисляет Finished по endsAt; отсутствие фоновой задачи не должно оставлять регистрацию открытой.

Состояние CANCELLED сохраняется в модели для удаления/серверных изменений; отдельная кнопка отмены события в мобильном MVP не задана, отдельный endpoint не придуман. Публичная доступность и регистрация не один флаг; скрытый/парольный event вне объёма.

Обложка загружается multipart `file`, ответ — assetId, размеры/MIME/byteCount/url. Сервер проверяет содержимое изображения, не только расширение и Content-Type; ограничивает decoded dimensions (предложение 40 MP), удаляет EXIF/геоданные, формирует безопасное preview. Техническое ограничение pixel count — часть серверной валидации 422 INVALID_IMAGE. Asset принадлежит uploader; attach чужого assetId → 422 INVALID_ASSET. Не принимать произвольные external URLs для server-side fetch. Черновой URL требует bearer; опубликованная обложка доступна публично по непредсказуемому asset URL. Обложка не должна требовать bearer стороннего origin.

Непривязанные assets удаляются через 24 часа; привязанные к draft/E сохраняются. Смена обложки не удаляет файл, используемый другим собственным объектом. Дополнительной публичной delete-ручки для GC не нужно. Повтор upload с тем же key и теми же bytes возвращает прежний asset; multipart boundary не входит в fingerprint.

## 7. Регистрация и билеты

### 7.1 Гость

POST guest содержит formVersion, name/email/phone, answers и consent. При новой регистрации сервер проверяет доступность/форму/согласие, выдаёт ticket и mail receipt одной логической операцией. Нет userId в команде, нет автоматического signup. Существование аккаунта само по себе не мешает новой регистрации на E: **предлагаемый финальный вариант по уточнению пользователя**. Это меняет нынешний demo `RequiresLogin`, описанный в старом S03; backend должен подтвердить именно эту развилку до T10. Аккаунт не раскрывается в ответе регистрации.

Новый билет: 201 ISSUED, GuestTicket с QR/manualCode и минимальными данными, email и mail status. Android сохраняет только компактный receipt текущего flow. Сворачивание/восстановление той же задачи Android допускает возврат к receipt; явное закрытие flow или новый запуск не открывают гостевой кабинет. Тело формы и secret idempotency key не превращаются в постоянный guest storage.

Если на этот email/E уже есть ACTIVE/USED, **новая** операция возвращает 202 EXISTING_REGISTRATION без чужого ticketId/имени/credentials. При допустимом cooldown отправляется существующий билет на сохранённый email. Введённые сейчас имя/телефон/ответы не заменяют прежние. Иначе любой знающий email мог бы украсть QR через повтор формы. Указание существующего email разрешено, но не является доказательством владения старым билетом. Повтор **исходной** операции с её непредсказуемым ключом — отдельное правило §10, он возвращает исходный QR.

Для восстановления письма — `ticket-email-requests {email}`, одинаковый 202 даже для отсутствующего E/регистрации. Это не поиск и не получение списка. Отправка только на сохранённый адрес, без произвольного `recipient`. По новому гостевому запросу с тем же email после CANCELLED можно создать новый билет, если регистрация открыта.

Гостевой PDF в Android последним уточнением отдельно не подтверждён: **анонимную download-ручку не вводим**. Письмо содержит PDF/код; внутри приложения PDF доступен после входа. Если вернём кнопку гостевого PDF, нужен отдельный ticket-scoped grant, не переиспользование QR или account access token. Это локализованное расширение, не обязательная задача сервера v1.

### 7.2 Вошедший пользователь

POST registrations не принимает email/userId: email берётся из подтверждённой сессии. name/phone подставляются клиентом из профиля и сохраняются снимком заявки. Если профиль требуется исправить, UI может вести в профиль; не создаём третий канал смены email через форму.

Уже существующий ACTIVE/USED → 200 `existing=true,ticketId,mail=null`, без второго места и без автоматической повторной рассылки. Этот ответ допустим даже после закрытия регистрации: это получение результата уже существующего участия, не новая заявка. При новой заявке → 201 `existing=false` и ненулевой mail receipt. Проверка существующей записи выполняется после auth и валидации синтаксиса, до проверки текущей открытости/старой формы. Для guest duplicate аналогично проверяем уже существующий билет до текущей доступности формы, но возвращаем только 202 без credentials; удалённые события не восстанавливаем.

Сопоставление гостевых заявок по email выполняет backend после подтверждения владения email. Старые Cancelled и история также видны владельцу почты. `registration.userId` может заполняться сервером, но критерием привязки не является переданный клиентом ID. Удалённые/анонимизированные данные не должны «оживать» при создании нового аккаунта на тот же email (§12).

Счётчик мест, уникальность неотменённой регистрации и создание ticket фиксируются согласованно на сервере. Отправка письма через transactional outbox/эквивалент: сбой почты не откатывает билет. От клиента не требуется реализовывать или доказывать серверные транзакции.

### 7.3 Чтение, отмена и история

`GET /me/tickets?view=CURRENT|HISTORY`, `GET /me/tickets/{id}`: только собственные tickets; чужой ID → 404. CURRENT = ACTIVE и событие ещё не Finished/Cancelled/deleted/по endsAt. HISTORY включает USED, CANCELLED, а также ACTIVE после завершения (`historyOutcome=MISSED`). USED → ATTENDED, CANCELLED → CANCELLED. Начало без конца не перемещает ACTIVE в историю.

Credentials возвращаются только для canDisplayQr=true. История не показывает QR. Гостевой уже выданный snapshot/старое письмо может содержать прежний QR — сервер всё равно отвергнет недействительный проход. Смена данных E не меняет QR/manualCode/номер; текущий запрос билета/PDF содержит актуальные title/date/venue. Имя участника/ответы остаются снимком регистрации, изменение профиля не переписывает историю.

Отмена собственного ACTIVE и owner cancellation одинаково переводят в CANCELLED, освобождают место ровно один раз. Уже CANCELLED → успешный прежний результат, даже без совпадения ключа. USED → 409 TICKET_USED. Предлагается сохранить demo: активный неиспользованный билет можно отменить и после начала/окончания; это не открывает регистрацию заново. Сервер возвращает canCancel из этой политики. Отмена уведомляет участника служебным письмом, но почтовый сбой не откатывает отмену.

## 8. Волонтёры и проверка прохода

Owner получает список активных grants с userId/name/email и `checkedInCount`: число первых успешных проходов, не попыток. Выдача прав по **явно типизированному** target EMAIL или USER_ID, без неоднозначного парсинга поля на сервере. Только существующий аккаунт; нет приглашений/автосоздания. Неподтверждённому можно выдать grant, но до подтверждения/login он не сканирует. Это предложение сохраняет текущую независимость grant и session.

Повтор grant возвращает `alreadyActive=true`; после revoke повтор grant активирует ту же связь и сохраняет прежний счётчик. Владелец всегда сканирует по владению, self-grant не нужен: grant/revoke на owner → 409 TARGET_IS_OWNER (отличие от permissive fake). Отзыв отсутствующего grant → 204. Только активный grant даёт canScan, отзыв проверяется на следующем запросе.

`scan-access` нужен для открытия/foreground сканера; он не выдаёт долговременное разрешение. Каждая команда check-in повторно проверяет право. При 403 Android закрывает scanner и очищает результат; personal ticket этого человека остаётся.

QR содержит случайную непрозрачную строку без ФИО/email/JSON/роли. Manual code отдельный: 12 символов `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`, отображение `XXXX-XXXX-XXXX`, сервер убирает ASCII-пробелы/дефисы и приводит к uppercase. Генерация CSPRNG с проверкой уникальности (предлагаем глобально); не производить из displayNumber, ticketId или demo hash. Code и QR показываются на текущем билете/письме/PDF, оба проверяют один ticket. `displayNumber` только для поиска/человеческого идентификатора.

Порядок POST check-ins:

1. Сессия и право на E, в том числе при replay; затем лимит частоты.
2. Нормализация/валидация credential, поиск билета. QR другого E → INVALID/WRONG_EVENT; не раскрывать имя/номер/владельца другого E.
3. CANCELLED → INVALID/CANCELLED. Неизвестный → INVALID/UNKNOWN.
4. USED → ALREADY_USED с неизменным first record, даже если E позже закончено.
5. ACTIVE на Finished/Cancelled/deleted или после endsAt → INVALID/EVENT_INACTIVE.
6. Иначе одна неделимая серверная смена ACTIVE→USED и запись checkerId/checkedAt с серверным временем. Закрытая регистрация и наступление startsAt сами по себе check-in не запрещают; ранний check-in после публикации разрешён по текущему demo default.

Все три бизнес-результата HTTP 200 и `outcome`. Ошибки прав, формата, сети/сервера не маскируются под INVALID. Не возвращать attendeeEmail/phone/answers в результате сканирования. Новый backend всегда создаёт first record; `null` для старых debug Used поддерживается только нынешним fake, не как нормальный успех сервера.

При двух разных операциях на один билет только одна ADMITTED, другая ALREADY_USED. Повтор потерянной **той же** операции возвращает исходный ADMITTED с тем же record и `Idempotency-Replayed:true`; Android показывает «Этот проход уже был зарегистрирован в …», а не новый зелёный допуск. Для реально следующего посетителя/нового scan создаётся новый key. Нельзя сохранить bool ADMITTED и восстановить его как разрешение после нового процесса.

## 9. Дашборд, файлы и письма

### 9.1 Явка и участники

Dashboard: registered=ACTIVE+USED, checkedIn=USED, notCheckedIn=ACTIVE, cancelled отдельно. Unlimited remaining=null, иначе capacity−registered. Счётчики не зависят от q/status/страницы. Все поля одного ответа из согласованного серверного снимка; updatedAt — изменение данных, serverTime — время чтения.

`GET attendees`: поиск case-insensitive substring по name или displayNumber, не по QR/manual. Ответ содержит contacts/answers только owner. Сортировка REGISTERED_DESC или NAME_ASC плюс ID; фильтр ALL/ACTIVE/USED/CANCELLED. Чек-ин, отмена, выдача/отзыв grant и изменение списка должны увеличивать dashboard.revision, даже если числовые totals не изменились. Экспорт не принимает поисковый фильтр.

Для первой production версии предлагаем **polling раз в 5 секунд, только пока dashboard видим**, плюс немедленный refresh после собственной мутации и foreground. Это обновление с задержкой до интервала + сеть, не обещание мгновенного push. При изменении revision перечитать видимую первую страницу и сбросить старый cursor; при ошибке сохранить данные с признаком устаревания/временем обновления. После ошибок интервалы 5/10/20/30 секунд, при выходе polling остановить. Tickets/MyEvents обновлять при открытии/foreground/своей мутации, без постоянного фона. Scan-access на foreground и раз в 15 секунд пока scanner видим, но право на каждой команде проверяется независимо.

SSE/WebSocket не нужны как вторая обязательная система в v1; если команда требует обновления быстрее 5 секунд, согласовать push отдельно за теми же repository Flow. Существующий fake моментально обновляет локальный store, что не доказывает синхронизацию двух устройств.

### 9.2 PDF/XLSX

Оба вида генерирует backend как DocumentJob. POST возвращает 202, jobId и snapshotAt; возможен сразу READY. Клиент опрашивает job по pollAfterSeconds (предложение 2 секунды). PENDING → READY или FAILED; через 24 часа EXPIRED. Отсутствие поля fileName/MIME/size отражается null до READY. Retry failed job — новый POST с новым key; повтор прежнего key возвращает прежнюю job.

Download — защищённый GET content, без публичного бессрочного URL и без access в query. MIME точный, Content-Disposition attachment с безопасным filename/UTF-8 filename*, Content-Length; ошибки JSON, не HTML. Range в v1 не обязателен: после разрыва можно скачать целиком заново. Сервер проверяет владельца задачи и актуальный доступ к source при status/download. Нельзя скачать экспорт после потери права или чужую задачу по ID.

PDF: только собственный текущий ACTIVE, содержит event title/date/timezone/venue, attendeeName/displayNumber, QR и manualCode; без ответов анкеты/телефона. Если к моменту download билет отменён/использован/событие закончено — TICKET_NOT_CURRENT, не выдавать ранее подготовленный активный QR. Уже скачанный файл не отозвать, окончательное решение всё равно при check-in. Изменение event metadata после snapshotAt не переписывает готовый файл; новая задача создаёт новый снимок.

XLSX: все регистрации E, включая Cancelled, независимо от поиска/страницы. Колонки: registrationId, displayNumber, name, email, phone, registeredAt, status, checkedAt, checkerName, formVersion, затем ответы по фиксированным questionId с заголовками. Никаких credentials. Время ISO UTC с отдельной timezone события; checkbox boolean, choice label вместе со стабильным optionId, text текст. Потенциальные формулы пользовательских строк пишутся как текстовые ячейки. Метаданные snapshotAt/eventId помещаются на отдельный лист. Экспорт отражает снимок job, не меняющуюся смесь страниц.

### 9.3 Email

Обязательные служебные письма: confirm, reset, билет, подтверждённая отмена, недоступность события при удалении owner. Пользовательский `emailNotificationsEnabled=false` выключает необязательные напоминания, не безопасность и не выдачу билета. Маркетинговые рассылки в MVP не создаём. Повтор билета требует отдельного явного запроса.

`QUEUED` означает сохранённую задачу доставки, `SENT` — провайдер принял отправку, не доказательство прочтения, `FAILED` — исчерпанная/известная ошибка. Android не должен писать «доставлено», когда сервер только поставил в очередь. Билет действителен независимо от результата письма. Backend повторяет transient failures очереди (предложение 1/5/30 минут, затем 2 часа, максимум 24 часа); постоянные отказы не зацикливает. Состояние mail не равно ticket.status. Для повторной выдачи Cancelled/Used/завершённого через гостевой recovery можно отправить письмо со статусом **без QR**, не переактивировать билет. Для private resend/pdf с такими ticket — TICKET_NOT_CURRENT.

## 10. Идемпотентность и потерянный ответ

`Idempotency-Key` — случайный UUID v4 на **логическую команду**, не на сетевую попытку. Обязателен у помеченных методов OpenAPI: выдача регистрации, save/publish/update, close/finish, grant, check-in, отмена, email request, upload, file job, update profile, deletion, signup/reset/refresh. GET, DELETE grant, confirm и logout имеют собственную безопасную повторяемость. Sign-in не повторять автоматически после сетевой неопределённости: пользователь может войти снова, это создаёт новую сессию, не второй билет.

Сервер хранит `(scope, method, canonical path, key, fingerprint, outcome)`. Scope private=userId, не accessToken, чтобы refresh не ломал повтор; guest=endpoint+key с дополнительными ограничениями event/email. Fingerprint — канонический body (для multipart MIME + digest file), не заголовки access/trace. Не логировать fingerprint inputs. Guest key является чувствительным proof исходной операции, а не публичным номером заявки. Проверить syntax/права/сопоставление actor до выдачи сохранённого результата.

Обычный срок хранения результата — **24 часа**. Та же команда и key → тот же HTTP/body, `Idempotency-Replayed:true`, без нового места, билета, письма, файла или прохода. Иной body с тем же key → 409 IDEMPOTENCY_MISMATCH. Пока выполняется → 409 OPERATION_IN_PROGRESS + Retry-After. Нельзя возвращать сохранённый успех после потери права на объект. Guest replay не выдаёт кабинет: возвращает только snapshot первоначальной операции при точном body/key. После expiry новой попытке нельзя обещать исходный receipt; сработают предметные ограничения повторной регистрации/Used.

Исключения: refresh и reset-verify возвращают чувствительную пару/grant только 60 секунд и не дольше срока самого секрета; encrypted response после этого удаляется. Остальные результаты с QR/персональными данными также хранятся зашифрованно и удаляются по TTL. Повтор успешного sign-up по key возвращает исходный challenge, даже если аккаунт теперь существует; не создаёт новый challenge. 401/403/422/429 и ошибки до выполнения не фиксируются как успешная операция. Коммит и durable outcome должны быть согласованы: после «записали, но потеряли ответ» сервер может восстановить именно исходный результат. Нельзя кэшировать случайный 500 навсегда.

Для успешного удаления есть узкое исключение: исходный bearer, уже отозванный этим удалением, и **тот же key/body** могут получить только тот же DeletionReceipt в пределах 24 часов. Никаких других данных/операций им не разрешается. Альтернатива проще для backend — не поддерживать этот recovery, но тогда Android честно считает 401 после неопределённого удаления неопределённым и проверяет результат повторным login; выбрать одно до реализации. В OpenAPI v0.1 выбран первый вариант.

Android блокирует двойной tap, держит key на время операции и явного retry. Новый key при каждом таймауте запрещён для check-in/submit. Серверная отмена операции из-за Android cancellation не обещается: закрытие экрана не откатывает уже созданный билет. Никаких автоматических очередей регистрации/прохода офлайн. Постоянное хранение анкеты гостя ради retry запрещено B04; после смерти процесса без receipt — письмо/кабинет, а не восстановление заявки.

## 11. Ошибки и лимиты

Пример:

```json
{
  "code": "VALIDATION_FAILED",
  "requestId": "req_4f39",
  "fieldErrors": [{"field": "phone", "code": "INVALID_PHONE", "params": {}}],
  "retryAt": null,
  "details": {}
}
```

| HTTP | Коды и смысл |
|---|---|
| 400 | INVALID_REQUEST, INVALID_CHALLENGE, CURSOR_INVALID: неправильный формат/секрет/несогласованный cursor |
| 401 | INVALID_CREDENTIALS; ACCESS_EXPIRED/INVALID; SESSION_REVOKED; REFRESH_INVALID/EXPIRED/REUSED |
| 403 | EMAIL_UNVERIFIED, FORBIDDEN, REAUTHENTICATION_FAILED; не отправлять клиента бесконечно в login при запрете на E |
| 404 | EVENT/DRAFT/TICKET/REGISTRATION/DOCUMENT_NOT_FOUND; ACCOUNT_NOT_FOUND только для owner grant |
| 409 | EMAIL_TAKEN; FORM_STALE; POLICY_CHANGED; REGISTRATION_CLOSED; CAPACITY_REACHED; REVISION_CONFLICT; QUESTIONS_LOCKED; EVENT_FINISHED; TICKET_USED/NOT_CURRENT; TARGET_IS_OWNER; DRAFT_PUBLISHED; IDEMPOTENCY_MISMATCH; OPERATION_IN_PROGRESS; DELETION_IMPACT_CHANGED; DOCUMENT_NOT_READY |
| 410 | CHALLENGE_EXPIRED/CONSUMED, CONFIRMATION_EXPIRED, CURSOR_EXPIRED, DOCUMENT_EXPIRED |
| 413/415 | FILE_TOO_LARGE / UNSUPPORTED_MEDIA_TYPE |
| 422 | VALIDATION_FAILED или INVALID_IMAGE; ошибки полей отдельным массивом |
| 429 | RATE_LIMITED + Retry-After в секундах и retryAt; без мгновенного повторения |
| 500/503 | INTERNAL_ERROR / SERVICE_UNAVAILABLE; никаких stack traces и DB ошибок в UI |

Стандартные field codes: REQUIRED, TOO_LONG, INVALID_NAME, INVALID_EMAIL, INVALID_PHONE, WEAK_PASSWORD, INVALID_DATE, INVALID_ZONE, CAPACITY_BELOW_REGISTERED, INVALID_ANSWER, UNKNOWN_QUESTION, DUPLICATE_ID, INVALID_ASSET. Путь поля: `questions[2].title`, `answers[questionId]`, `phone`. REGISTRATION_CLOSED.details.reason — enum доступности. REVISION_CONFLICT.details.currentRevision и FORM_STALE.details.currentFormVersion — текущие версии. Чужие объекты не раскрывать через details.

Лимиты предложения, централизованная серверная конфигурация, ответы никогда не требуют зашитого таймера Android:

| Операция | Начальная настройка |
|---|---|
| login | 5 неудач/15 минут по нормализованному email+IP, дополнительно 30/IP/15 минут; не блокировать весь аккаунт навсегда |
| signup, confirm/reset request | cooldown 60 секунд/email/назначение; 5 писем/час/email; 30 запросов/час/IP; для неизвестного email те же ответы/cooldown |
| reset verify | 5 неудач/challenge, дополнительно 30/IP/час |
| guest submit | 10/IP/минуту, 5 попыток/email+event/10 минут; корректировать для общей сети мероприятия, не выдавать дубль QR |
| ticket resend/recovery | 60 секунд/ticket, 5/час/ticket, 30/IP/час; не раскрывать наличие регистрации различающимся 429 |
| check-in | 120/минуту/scanner+event; дополнительно 20 неверных manual-кодов/минуту/scanner+event. Обычные QR successes не входят в этот дополнительный лимит |
| export / PDF | 3 XLSX/10 минут/owner+event, 10 PDF/час/user; polling в 5 секунд должен укладываться в read limits |

Значения не объявляются проверенными нагрузочным тестом. Backend измеряет и согласует поправки. Доменная ошибка check-in Invalid не даёт клиенту права игнорировать 429. Нет CAPTCHA/отдельной антибот-системы в мобильном контракте v1; если лимитов недостаточно, это согласуемое расширение.

## 12. Профиль, удаление и ссылки

Профиль: GET/PUT `/me`; email/id/emailVerified неизменяемые со стороны формы. name/phone/organization/emailNotificationsEnabled сохраняются с revision. Уведомления не объединяются с согласием на terms/privacy. UserId можно копировать для выдачи grant; это не секрет и не достаточная авторизация.

**Удаление — предложение, требует отдельного продуктового согласования до реализации разрушительного действия.** Принят только явный диалог с паролем и раскрытием последствий; точный каскад ранее оставался открытым. Предлагаем:

1. Preview без пароля возвращает counts и confirmationToken на 10 минут, привязанный к текущей сессии и точному набору затрагиваемых объектов. Не просто число: новые регистрации/события меняют снимок. UI явно сообщает об удалении созданных событий и недействительности чужих билетов на них.
2. POST deletion с текущим password/token/confirm=true; если последствия изменились — 409, новый preview и новое подтверждение. Неверный пароль → 403. Ничего не удаляется предварительным preview.
3. До ответа 202 сервер закрывает все сессии/права аккаунта; собственные события становятся недоступны/терминальны, их ACTIVE tickets отменяются; новые заявки и check-in запрещены. Его собственные ACTIVE tickets на чужие события отменяются с освобождением мест. USED сохраняются как факт посещения без восстановления credentials; used-counts не уменьшаются. Grants отзываются. Черновики удаляются.
4. У остальных участников сохраняется минимальная запись истории со статусом отмены/удалённым событием; им ставится служебное уведомление. Физическое удаление/анонимизация фоновые, доступ уже закрыт. QR по отменённым не проходит. Удаление checker не уничтожает first check-in другого участника, но checkerId/name могут быть null, UI «Удалённый пользователь».
5. Стираются/анонимизируются профиль, credential hashes, контакты и идентифицирующие ответы удаляемого участника, там где они больше не нужны по согласованной политике хранения. Повторный signup того же email — новый аккаунт, прежние удалённые tickets/grants не присваиваются заново. Идентичность связывается с поколением аккаунта/удалением, не только вечным email lookup.

Backend и владелец продукта должны утвердить сроки удаления из основной БД, backup и аудита, а также допустимые сохраняемые сведения. Здесь не придумывается юридический срок и не заявляется соблюдение законодательства. Это **единственный существенный разрушительный продуктовый блок**, который нельзя молча считать согласованным; остальные API можно разрабатывать независимо.

Production URL под контролем команды:

| Путь web/App Link | Назначение |
|---|---|
| `https://<web-host>/e/{eventId}` | Публичная страница E; при установленном Android открыть общий EventDetails |
| `https://<web-host>/confirm/{challengeId}?token=...` | Только доставка verify proof; выполнение через POST confirm, после — ручной login |

Backend размещает `/.well-known/assetlinks.json`; Android передаёт окончательный applicationId и SHA-256 signing certificate. Домены API/web могут отличаться; не считать demo scheme production-настройкой. Для отсутствующего приложения нужна минимальная web-страница события/подтверждения или согласованный fallback. Это инфраструктура backend/web, не новая Android-фича. Сброс по коду, отдельный reset-link/произвольный returnUrl не нужен. Письмо с билетом содержит PDF/QR и ссылку E, не account session. Referrer/logging/аналитика confirm-страницы не должны передавать token третьим сторонам.

## 13. Изменения Android при подключении

Это не обещание заменить одну строку URL. `data:remote` реализует существующие repository ports; transport DTO отдельно от domain, DI выбирает demo/remote. VM/Compose не получают HTTP, токены или DTO. Полный mapping — [coverage](api/coverage.md).

Обязательные изменения: production session restore/refresh/storage и distinction access/session expiry; guest existing-email branch; email normalization; явный idempotency operation context и replay check-in; consent versions; серверный manualCode вместо demo derivation; pagination/freshness; URL-backed covers; profile/document/attendance ports под T08–T10; удаление после согласования. Не менять fake schema 4 или текущую сборку только из-за публикации этого документа. Общие бизнес-invariant tests должны проходить на обоих адаптерах; особенности транспорта проверяются отдельно.

## 14. Порядок backend-разработки и критерии готовности

1. **Согласование контракта:** отметить поддерживаемые предложения §15, выбрать домены и staging, исправить DTO вместе. Не ждать полной реализации сервера.
2. **Первый вертикальный путь:** config, auth/signup/confirm/login/refresh/reset/logout/me, public E, guest/auth registration, me tickets/cancel, реальные тестовые письма. Android подключает T04/T05 к staging, включая восстановление сессии.
3. **Организатор:** drafts, публикация, редактор, cover, MyEvents, закрытие/завершение.
4. **Волонтёры/проход/явка:** grant/revoke, scan access/check-in, dashboard/attendees/cancel; обязательная проверка двумя устройствами.
5. **Завершение:** профиль, PDF/XLSX, повтор писем, согласованное удаление, production App Links, ограничение нагрузки и наблюдаемость.

Приёмочные сценарии backend/staging (не заявление, что они уже пройдены):

- Пользователь владеет A, сканирует B, участвует C и одновременно участвует/сканирует D; прямые HTTP-вызовы не обходят ограничения.
- Гость получает билет без аккаунта/verify; новый запрос известного email не раскрывает старый QR; исходный retry не создаёт второй билет. Последующий signup/confirm/login получает нужные билеты, не чужие.
- Confirm без login; reset без предварительного verify; код одноразовый/ограничен; reset отзывает все прежние access/refresh.
- Параллельные Android-запросы делают один refresh; потерянный refresh response безопасно восстанавливается в окне; reuse за его пределами отзывает семью. Logout запрещает старый access немедленно.
- Две регистрации на последнее место: один успех; отмена дважды освобождает один раз. Это тест сервера, не задача моделирования распределённой транзакции в Android.
- Потеря ответа после регистрации/publish/check-in/mail job не создаёт дубль при одинаковом key. Смена body отклоняется. Повтор check-in отличается от следующего scan Used.
- Первая регистрация фиксирует вопросы, даже если затем все отменены; stale revision/form не затирают данные. Started/Finished и null endsAt проверены серверным временем.
- Два сканера дают один first record; revoke запрещает следующий запрос; чужой QR не раскрывает PII; timeout не выдаёт зелёный допуск.
- Поиск/пагинация не меняют totals; экспорт содержит все статусы и все вопросы, не только страницу; формулы ячеек безопасно представлены текстом.
- PDF/job/участники/чужой draft недоступны по подбору ID; обложка проверяется как изображение; access не уходит на сторонние URL.
- После принятой политики удаления нет доступа и повторной привязки удалённых данных; уведомления другим участникам не теряются из-за очереди.

Для staging нужны demo-эквивалентные fixtures (owner/volunteer/participant), события open/full/closed/started/finished, билеты Active/Used/Cancelled/WrongEvent, sandbox почта и способ контролируемо воспроизвести timeout-after-commit. Не переносить dev пароли/seed/reset/debug endpoints в production. Тестирование настоящей рассылки и разрушительных действий выполняется только на выделенных тестовых данных.

## 15. Что согласовать, не блокируя весь backend

| Решение | Наш конкретный вариант | Когда ответ необходим |
|---|---|---|
| Session protocol/TTL | opaque access 15 мин, rotating refresh idle 30 дней/absolute 90, replay 60 сек | До auth integration |
| Гость на существующий email | Новая регистрация разрешена; старый билет не раскрывается без proof/login, отправляется письмом | До registration integration; текущий fake отличается |
| Email normalization | case-insensitive адрес без provider rewrites, IDNA domain | До схемы уникальности аккаунтов/регистраций |
| Check-in credential/time | random opaque QR + random 12-char manual, check-in после публикации и до завершения | До T07 remote |
| Dashboard freshness | polling 5 секунд в foreground | До T08 remote |
| Файлы/guest PDF | Backend jobs для private PDF/XLSX; guest PDF только в письме | До T09 files |
| Deletion cascade/retention | Preview+пароль; каскад и анонимизация по §12 | До реализации удаления; не блокирует auth/events/check-in |
| Инфраструктура | staging/API/web host, email sender, signing association, terms/privacy | Домены/почта до сквозной интеграции, реальные соглашения до внешнего запуска |

Остальные размеры, cooldown и имена ручек уже предложены, не оставлены россыпью открытых вопросов. Если backend принимает этот комплект, можно реализовывать по нему и фиксировать согласованные поправки новой версией.

## 16. Проверка самого комплекта

Команда: `python scripts/verify-api-contract.py`. Проверяет локальные `$ref`, JSON Schema 2020-12, соответствие path parameters, уникальность operationId, документирование методов, валидные/невалидные примеры и покрытие operationId в карте сценариев. Полная проверка OpenAPI выполняется отдельно через `openapi-spec-validator`, если доступен; результат текущего запуска записан в [coverage](api/coverage.md). Структурная валидность не доказывает серверную авторизацию, транзакции, безопасность или достижение latency.

Спецификация использует [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html), а не заявляет её самой новой версией. Код приложения, fake snapshots, версии сборки, CODE_REVIEW и человеческие H-приёмки этой документационной задачей не изменяются.
