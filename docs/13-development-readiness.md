# Аудит готовности к разработке

Дата: 27 октября 2026. Объём: документация, её согласованность и пригодность для старта Android-разработки. На момент проверки в рабочей папке только README, AGENTS и docs; Git/Gradle/Android-исходников нет. Код, APK и совместимость зависимостей этим аудитом не проверялись.

## Вывод

Можно начинать **T01 — технический каркас**. Для одновременного выполнения всего MVP разными агентами документацию нельзя считать полностью однозначной: часть технических соглашений отсутствовала, а план и тесты содержали более сильные обещания, чем согласованный API. Ни один из оставшихся вопросов не требует ждать полного backend перед каркасом/UI-kit.

Качественный старт здесь означает проверить архитектуру маленьким работающим срезом и затем развивать её. Объём текста сам по себе не доказывает готовности. Первые доказательства — воспроизводимая сборка, одна ViewModel через Hilt, корректная навигация/восстановление и проверяемые компоненты UI.

## Что уже достаточно определено

- Границы MVP и исключения MAX/архива, 18 mobile-frame и ссылки на них.
- Один аккаунт и независимые права на E; общий scanner/MyEvents/EventDetails.
- Актуальный гостевой сценарий: QR сразу, без автоаккаунта, временное сохранённое состояние, затем письмо/кабинет.
- Ответы B01–B08: optional российский телефон, имя на любом языке, без сохранения анкеты перед входом, ручной вход после подтверждения.
- Общие репозитории/fake вместо независимых статичных ответов экранов, схема замены на API.
- UI-токены и начальные компоненты; разделение автоматической логики и человеческих H1–H4 проверок.

## Что закрывается перед первым кодом, что — кодом

**Документами уточнено:** MVVM и границы зависимостей, разделение guest/auth исходов, правила saved state, ошибки/retry, маршрут чтения, минимальная готовность задачи. Эти defaults можно использовать для реализации и изменять с фиксацией причины.

**В T01 нужно доказать:** выбранные версии действительно собираются; DI создаёт ViewModel; три таба и вложенный экран не дублируют стек; entry state корректно сохраняется/очищается; доступны воспроизводимые build/check commands. Без этих результатов нельзя утверждать, что технический фундамент готов.

**Перед конкретными фичами:** поля GuestTicketSnapshot и screenshot QR, поведение законченного/отменённого события, новые layout поверх UI-кита, тексты предупреждений потери анкеты, условие доступности экспорта/файлов. Гостевой PDF пока не согласован — не показывать неработающую кнопку.

**Перед API:** формат session/refresh/errors, время и timezone, QR/manual credential, поддержка retry/requestId, файлы/realtime/удаление. Это локальные интеграционные зависимости; изменения пользовательского сценария согласовывать отдельно.

## Минимальный разумный порядок

1. T01: одна собираемая структура MVVM + DI + навигация, один demo data port, проверка ownership/state. Не разрабатывать одновременно весь fake/backend/UI.
2. T03 и узкий T02: визуальные примитивы, debug-галерея, event/guest submit. H1 проверяет общие компоненты до массовой сборки экранов.
3. Первый пользовательский срез: открытая страница → форма → guest submit → QR → соседний экран/Back → recreation → явное закрытие без постоянного guest доступа. Показывать loading/error/no places, а не только happy path.
4. Отдельная регистрация аккаунта → подтверждение → ручной вход → все билеты на email. Затем организатор/волонтёр/дашборд по плану.

Новые крупные документы, автоматическая UI-ферма, полная OpenAPI-схема, десятки feature-модулей, продвинутая телеметрия и универсальный state framework сейчас не нужны. Возвращаться к ним только при конкретной потребности.

## Пределы этой проверки

Прочитаны структура и рабочие спецификации проекта, сверены актуальные ответы, результаты/порты, план и проверки. Найденные расхождения исправлены в соответствующих документах. Проверены локальные ссылки и структура Markdown после правок.

Не выполнялись: повторный live-осмотр Figma, компиляция/Android lint/unit/device tests, проверка установленного SDK/JDK заново, оценка реального API или его безопасности, полноценный рендер Mermaid. Внешние технические сведения о lifecycle/state сверены с официальными Android-источниками, ссылки приведены в 14.
