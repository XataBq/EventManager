# Проверки: агент и человек

**29 октября:** отдельный auth smoke T04 на APK 0.4.3-t04-demo/code 7 подтверждён пользователем («Проверил, замечаний нет»), T04 — DONE. H2 для нового среза T05/code 8 остаётся ожидающей; [его чек-лист и автоматические доказательства](19-t05-validation.md). Строки M ниже агентом не отмечались пройденными.

Цель — автоматизировать дешёвые проверки логики и передать визуальную/устройственную приёмку человеку. Полный обход приложения агентом через GUI не является обязательным шагом каждой задачи. Проверки технического каркаса T01 описаны отдельно в [15-t01-validation.md](15-t01-validation.md); продуктовая A/M-матрица ниже ещё не пройдена.

## Ответственность агента

1. Сборка изменённого варианта, lint и небольшой релевантный набор unit/contract tests.
2. Проверка матрицы прав, исходов проверки билета/мест, билетов по email после отдельного создания аккаунта и очистки сессии. Серверные транзакции регистрации не входят в Android-проверки; pending registration исключён по B04.
3. Предоставить APK, build id, reset/seed, тестовые аккаунты, QR-примеры и список действий для человека.
4. Подготовить Compose previews и debug-галерею; screenshots приложить, если они уже получены, но не гонять дорогое визуальное сравнение без изменения UI.
5. При дефекте добавить узкий regression test, если проблема относится к состоянию/логике. Не тестировать геттеры и копии implementation.

После T01 точные команды записать в README. Ожидаемые имена для выбранной структуры (пока не запускать и не выдавать за существующие):

```powershell
.\gradlew.bat :core:domain:test :data:fake:test
.\gradlew.bat :app:assembleDemoDebug :app:lintDemoDebug
```

Если модуль fake становится Android-модулем, фактическая задача unit tests может отличаться — агент T01/T02 обязан заменить пример реальной командой. Полные instrumentation/UI tests добавлять адресно для навигации и lifecycle, если unit tests не покрывают риск; массовые screenshot tests до стабилизации дизайна не нужны.
