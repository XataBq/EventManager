# EventPass — необходимые доработки backend

Версия 1.2, 13 ноября 2026. Основа — `EgorDikanskiy/eventpass`, коммит `94af06fb82e432308e4425f01447018d8641ca72`. Android App Links отложены по решению пользователя 13 ноября.

Ниже перечислены необходимые расширения текущего `/api`. Предлагаемые пути можно заменить эквивалентными с тем же поведением и отразить в серверном OpenAPI.

## Функциональные доработки backend

### BK01. Время окончания и ручное завершение

**Сейчас:** finished вычисляется как startsAt + 4 часа. Нет endsAt и команды завершения.

**Нужно:**

- Добавить nullable `endsAt` в хранение, EventInput/Create/PATCH и EventSummary/Details/TicketEvent. Если endsAt задан, он позже startsAt. Если `endsAt` отсутствует или равен null, окончание по умолчанию — `startsAt + 4 часа`. Если `endsAt` задан явно, использовать его.
- Хранить факт ручного завершения, например `finishedAt`; добавить owner-only `POST /events/{id}/finish`. Повтор возвращает то же завершённое E без повторных последствий. Это завершение E, а не скрытая кнопка «закрыть регистрацию».
- Итоговое время окончания: `effectiveEndsAt = endsAt ?? (startsAt + 4 часа)`. Статус draft до публикации; finished после ручного завершения или при `now >= effectiveEndsAt`; иначе published/live по startsAt. Ручное завершение имеет приоритет; уже завершённое вручную E не оживает от PATCH даты.
- После finished новые регистрации и первый проход запрещены; ранее USED и история сохраняются. Остальные правила scanner finished можно оставить серверными: 403 для недоступного сканера; Android адаптирует исход.

### BK02. Неполные черновики и публикация

**Сейчас:** draft использует обязательную модель полноценного EventInput.

**Нужно:**

- Существующие POST/PATCH events должны сохранять неопубликованный E с пустыми title/location/description, отсутствующей startsAt/capacity, незавершёнными questions/options. Null для поля черновика не означает unlimited у опубликованного E.
- Проверять типы, максимальные размеры и принадлежность owner всегда; обязательность бизнес-полей/даты/положительный capacity/валидность options — только на publish и при сохранении опубликованного E.
- Draft response должен честно передавать незаполненные поля; сортировка/списки не падают на null startsAt. Slug назначать/стабилизировать не позднее публикации без потери id. Один сохранённый draft при повторной публикации не создаёт второе E.

### BK03. Отмена участника организатором

**Сейчас:** `/tickets/{id}/cancel` разрешён только владельцу самого ticket.

**Нужно:** добавить `POST /events/{eventId}/attendees/{ticketId}/cancel` либо расширить текущую отмену с эквивалентной owner-проверкой. Проверять actor/event/ticket; owner E1 не отменяет ticket E2. ACTIVE→CANCELLED, повтор CANCELLED успешен, USED отклоняется. Самостоятельная отмена сохраняется.

Изменение статуса/счётчиков выполняется согласованно с конкурентным scan. Отмена не создаёт «свободное место» дважды, не удаляет анкету/историю, не меняет QR другой регистрации. При новой регистрации после отмены выдаётся новый ticket по текущей серверной логике.

### BK04. Загрузка и хранение обложки

**Сейчас:** coverUrl в response есть, upload/полей БД/attach в EventInput нет.

**Нужно:** авторизованный multipart upload, например `POST /assets/event-covers`, поле `file`; JPEG/PNG до 5 МиБ, необязательная обложка. Ответ: `assetId`, `url`, `mimeType`, `byteCount`, width/height. Добавить `coverAssetId` или эквивалентную защищённую привязку в draft/event POST/PATCH и возвращать рабочий coverUrl.

Проверять реальный MIME/изображение/размеры, права на attach; не принимать чужой asset и произвольный путь Android. Удалять EXIF/геоданные; UI показывает crop 16:9. `null` удаляет привязку. Хранить в S3/существующем asset storage с очисткой непривязанных загрузок и файлов удалённых событий; не удалять ещё используемый asset. Опубликованная обложка доступна гостю, URL draft не раскрывает его данные.

### BK05. Программа мероприятия

**Сейчас:** sections есть в модели ответа как пустой default, но не сохраняются запросом/БД.

**Нужно:** принимать/сохранять `sections: [{id,title,time}]` в черновике и E, возвращать на публичной странице. Plain text, порядок массива сохраняется; `time` — подпись программы, а не отдельный источник lifecycle. Пустой массив допустим, неполные элементы draft допустимы в рамках лимитов.

### BK06. Совместимость анкет и исторические ответы

**Сейчас:** поддерживаются text/textarea/email/tel/number/date/choice/select/multiple, но нет одиночного checkbox с boolean-ответом, используемого Android.

**Нужно:** добавить тип `checkbox` и boolean-ответ для него, required checkbox требует true; false допустим для optional. Остальные server types/лимиты принимаем, Android адаптирует renderer/редактор; не требуем переименовать всё в TEXT/SINGLE_CHOICE и не требуем один option вместо существующего минимума двух.

Сохранить уже существующий snapshot `answer_labels` и расширить его при необходимости: после rename/delete/type change старые answers и исходные названия/выбранные варианты доступны для экспорта. Если один question ID меняет смысл/тип, старый ответ не интерпретируется как новый тип. Не удалять старые значения при правке формы. Unknown/stale ответы, которые невозможно принять, должны давать ошибки конкретных вопросов; не обещать, что клиент может отправить молча проигнорированные обязательные данные.

### BK07. Настоящий XLSX

**Сейчас:** `/events/{id}/attendees/export` фактически отдаёт только CSV.

**Нужно:** сохранить CSV для web и добавить формат `?format=xlsx` или отдельный прямой XLSX download. Реальный OOXML `.xlsx`, MIME `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`, Content-Disposition с корректным именем; без DocumentJob API.

Экспорт owner-only, все tickets/статусы/исторические ответы E, независимо от search/page UI. Минимум: ticketId/code, fullName/email/phone при наличии, время регистрации, status, checkedInAt/checker при наличии, вопросы и сохранённые ответы. SnapshotAt/E metadata указать в файле. Пользовательские строки — text cells, не исполняемые формулы. Отсутствующая информация остаётся пустой, а не выдумывается.

Если телефон/контактные поля регистрации нужны в экспорте, сохранять их снимком на момент регистрации; позднее изменение профиля не подменяет исторический контакт. XLSX из сохранённого снимка не должен смешивать разные состояния между страницами.

### BK08. Согласованное чтение дашборда и число проверок волонтёров

**Сейчас:** stats и attendees независимы, offset-страницы меняют порядок от check-in; у Volunteer нет его checkedInCount, только scanner.checkedByMe текущего actor.

**Нужно:**

- Добавить непрозрачную `revision`/эквивалентный consistency token к stats и attendees. При check-in/регистрации/отмене/другом изменении отображаемых данных token меняется. Если клиент запрашивает следующую страницу старой версии, возвращать различимый STALE_PAGE/409, чтобы он перечитал первую страницу. Полноценный cursor API не обязателен, page/pageSize остаются.
- В отдельном ответе totals/page данные согласованы, tie-breaker ID стабилен. Не требуется мгновенный push: Android сам выполняет refresh/foreground/polling по потребности. `updatedAt`/`serverTime` полезны для freshness, но не заменяют version token.
- В `/volunteers` добавить `checkedInCount`: количество первых успешных allowed для данного checker/E. Revoke/regrant сохраняют существующую доступную историю. Не считать Invalid/AlreadyUsed как новый проход.

Cancelled по-прежнему могут отсутствовать в обычном attendees list, как сейчас на сервере; они должны сохраняться в экспортируемых данных. Обязательные filters/cursor и полностью иной порядок списка из старого OpenAPI не требуются.

### BK09. Согласие при создании аккаунта и заявке

**Сейчас:** согласие есть в web UI, но не передаётся/не фиксируется backend-командой.

**Нужно:** добавить consentAccepted и серверное acceptedAt к signup/registration, проверять согласие там, где оно обязательно в форме. URL/версии terms/privacy передать Android в конфигурации или существующем API-поле; хранить принятые версии, если тексты версионируются. Отдельный универсальный `/config` не обязателен. Гостевой автоаккаунт учитывает согласие исходной регистрации, не требует фиктивного отдельного signup.

## Технические условия интеграции

### IN01. Ошибки без разбора русского текста

Существующую оболочку `{code,message,fields}` и имена HTTP-ручек оставляем. Для новых и неоднозначных бизнес-веток нужны стабильные коды, например EVENT_FINISHED, TICKET_USED, STALE_PAGE, RATE_LIMITED, INVALID_IMAGE. Конкретные имена согласовать в OpenAPI. Для поля — различимый машинный issue, когда от него зависит поведение UI. Android отображает свои русские resources, не разбирает `message` для принятия решений. Диагностический requestId полезен; сложная новая error envelope не требуется.

### IN02. Потеря ответа и безопасный повтор

Существующие блокировки/unique constraints сохраняем. Для create event, регистрации и scan нужно определить повтор одной логической команды после timeout: **тот же результат без новой записи/прохода**. Предлагаем Idempotency-Key с сохранённым outcome и fingerprint body, разные ключи — разные команды. Срок хранения результата выбрать и зафиксировать сервером; исходный ориентир 24 часа, это техническое предложение, не новое продуктовое правило.

Новый scan USED должен вернуть already_used, а replay исходной потерянной операции — исходный record с явным replay-признаком, который Android не интерпретирует как новый допуск. Права на объект проверяются и при replay. Ограничения повторов и возвращаемые результаты должны быть явно описаны в серверном OpenAPI.

### IN03. Лимиты запросов

В поставляемом коде/proxy нет общего rate limiting. До внешнего запуска нужны серверные ограничения login/setup/reset/повторной отправки auth-ссылок/registration и scan manual EVT-xxxxxx, с 429 и понятным временем повтора. Особенно важен ручной шестизначный номер. Конкретные значения backend выбирает под нагрузку; фиксированные лимиты из старого Android-предложения не навязываем.

### IN04. Staging и OpenAPI

- Предоставить стабильный staging HTTPS API URL и его `/api/openapi.json`, тестовые аккаунты/события/почтовый sandbox; подтверждение, какая версия размещена. Код в GitHub сам не означает доступное Android окружение.
- Сохранить существующие web пути `/e/{slug}`, `/account-link#token=...&action=...`, guest ticket link. Android verified App Links и настройка ассоциации домена с приложением отложены; для текущей интеграции их готовность не требуется.
- Для ticket/PDF/новых файлов — явная проверка текущей session/guest capability, правильные MIME и HTTP-ошибка при недоступном storage. JSON с secrets/PII и auth/file responses не должны становиться общедоступным кэшем; применить no-store по назначению.
- Дополнить существующие API/browser tests новыми сценариями BK01–BK09. Первый проход двух scanner, отмена/проход, отзыв, storage/SMTP failures и ID-изоляция проверяются на staging/тестовых данных. Удаление аккаунта — только выделенные тестовые аккаунты, не реальные пользовательские данные.
