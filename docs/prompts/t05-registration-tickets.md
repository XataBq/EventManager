### 1. Общие порты и fake — следующая итерация T02

- Сейчас есть observe/refreshPublicEvent, submitGuest и observeMyTickets. Добавь только нужные операции: авторизованная регистрация, отмена собственного билета и чтение собственного билета при необходимости. Уточни исходы загрузки/ошибки/availability и политики полей, которых пока не хватает реальным экранам. Псевдо-Kotlin из docs/05 — ориентир, не требование создавать все перечисленные порты.

- Guest submit по новому email выдаёт snapshot и demo письмо **без создания аккаунта**. Существующий account → RequiresLogin без сохранения анкеты. Повтор активной/использованной гостевой регистрации → безопасный ExistingRegistration без ticketId/повторного QR: билет нельзя восстановить по знанию email/ID.

### 2. Persistence данных fake-сервера

- Перед H2 созданные registrations/tickets и их статусы должны переживать новый процесс и logout: после отдельного Login билет остаётся на email. Это сохранение данных **fake-сервера**, не постоянный гостевой кабинет.
- Используй небольшой versioned snapshot/адаптер, согласованный с существующим auth snapshot и единым Mutex. Сохрани совместимость с созданными T04 demo-аккаунтами: существующие proof/challenges не теряются при записи tickets и наоборот. Если схема меняется — явно обработай прежнюю схему; не сбрасывай данные при каждом запуске или ошибке чтения.
- IO вне main, ожидаемые ошибки storage типизированы. Не сообщай об успешной заявке/отмене до гарантированного сохранения её результата; при отказе не публикуй ложный билет, письмо или освобождение места. Существующие cancellation/generation/Mutex регрессии auth должны сохраниться. Не возвращай блокирующий Java-монитор вокруг IO.
- Не persist активную сессию, незавершённую анкету, UI flow или клиентский GuestTicketSnapshot-доступ. Запись ticket с QR payload в закрытых данных fake-сервера допустима; **гостевой UI не загружает её по email/ticketId после потери flow**. Собственный список/билет доступны только через repository guard после входа.
- Reset/seed явно доступны в demo tools; тесты получают изолированное хранилище. Outbox имитирует письмо и не является продуктовым способом получить чужой билет. Полные будущие server tables/Room engine, drafts editor и checkIns заранее не создавай.

### 3. EventDetails и форма

- Замени временный EventReceiver в public/private навигации общим рабочим EventDetails. И cold, и warm `eventpass-demo://demo/e/{eventId}` открывают тот же сценарий без дублей; неизвестный ID → NotFound. Не делай каталог/четвёртый таб.
- Различай загрузку, готовые данные, отсутствие E, ошибку/повтор, full/closed/started/finished и уже имеющийся собственный билет. Unknown не равен Unlimited. При refresh сохраняй видимые данные, где это уместно; отправка отдельно в loading, двойное нажатие не создаёт второй клиентский запрос.
- Guest: имя, email, optional российский телефон и динамические text/checkbox/single-choice вопросы, consent. Используй существующую централизованную валидацию/policy; имя любой письменности, не требуй два слова. Required/Optional/Hidden для телефона переключаются централизованно и отражаются в UI, без потери старых билетов.
- После Login email принадлежит аккаунту/read-only; данные профиля подставляются в доступном объёме, вопросы/consent остаются предметными условиями заявки. Не реализуй профиль CRUD ради этого среза и не запрашивай телефон повторно, если принятый сценарий его не требует.
- RequiresLogin ведёт в существующий Login с допустимыми email/eventId; **перед уходом очищаются ответы формы**. После ручного входа — E с новой пустой анкетой, без автоматического submit. Переход в профиль/уход с формы/смерть процесса тоже не восстанавливает ответы. Одна ViewModel в back stack сама по себе не должна случайно сохранять их вопреки B04.
- StaleForm → понятная ошибка и обновление формы без обещания переноса ответов; Timeout/Network не равны Full/успеху, автоматического retry мутации нет. Тексты из ресурсов, домен не знает R.string/русских ошибок.

### 4. Гостевой результат и срок жизни QR — ключевой риск T05

- G02 сразу показывает **настоящий QR из qrPayload успешного submit** и сообщение «Билет отправлен на почту» (в demo письмо обозначено имитацией). Нет обещания автоматически созданного аккаунта. QR должен декодироваться обратно в тот же payload; картинка-заглушка/номер вместо QR не подходят.
- До перехода к receipt запиши **компактные сериализуемые поля snapshot** у владельца guest flow в SavedStateHandle. Domain остаётся чистым Kotlin; Android encoding — на границе UI. Не сохраняй Bitmap/PNG, полный API response или ответы анкеты. Payload не клади в route/URL/обычный лог; в route только flowId/ID.
- Один владелец на guest receipt/fullscreen и нужные соседние экраны. При Back с fullscreen/входа/регистрации к сохранённому receipt QR тот же, без нового submit и без чтения произвольного билета из fake-сервера. Отделяй выданный билет от очищаемой формы.
- Activity recreation и **OS process death с восстановлением той же задачи** возвращают QR из saved state. Учти, что T04 начинает с SessionGate.Loading и новый процесс Guest: это не повод удалить публичный guest flow/saved state. Восстановленный приватный стек, напротив, не обходит session gate.
- Явное закрытие/удаление исходной flow entry очищает snapshot и связанные QR entries. Новый визит получает новый flowId и не наследует payload удалённой записи, в том числе при анимации pop. Завершение задачи и новый запуск не восстанавливают guest билет. Background/обычный поворот не считаются закрытием.
- Нет отдельного постоянного guest cache, кнопки «найти билет по email» или guest lookup по ticketId. После закрытия — письмо либо отдельный аккаунт/подтверждение/ручной Login. Переход к авторизованному кабинету использует TicketRepository, а не переносит гостевой snapshot в доверенные данные аккаунта.
- Для QR выбери небольшой encoder с проверенными первичными источниками/лицензией и совместимостью с текущим стеком; зафиксируй версию. Генерацию тяжёлого изображения вынеси из main, кэш только временный. Камеру/ML Kit/check-in не добавляй. Fullscreen QR закрывается Back без нижних табов; текст/номер помогают доступности.

### 5. Tickets и отмена

- Реализуй P02 из существующего root Tickets: список/выбор, текущие и история, пустые состояния без каталога, экран/карточка выбранного билета, fullscreen QR, переход к общему E, подтверждение отмены Active и состояния операции/ошибки.
- Классификацию текущих/истории делай по согласованным lifecycle/времени события и статусу билета; startsAt не означает Finished. Cancelled/Used показываются явно и не выглядят как активный билет для входа. Не придумывай возможность отмены Used.
- Подписки используют общий store: submit/cancel сразу меняют список, available places и выбранный билет без независимых счётчиков. При исчезновении выбранного элемента выбери безопасное состояние. ID выбора можно восстанавливать, но данные всегда перечитываются через guard; logout/смена аккаунта уничтожают приватных owners и данные, как в T04.
- PDF/Wallet/экспорт относятся к T09/вне MVP. Не показывай «скачано» без файла; скрывай неподдерживаемое действие или обозначай честный остаток. Гостевой PDF не согласован.
