## Последовательность реализации

### 1. Один рабочий срез данных

Сначала докажи: владелец E наблюдает dashboard → существующий CheckInRepository отмечает ACTIVE как USED → тот же dashboard и личный билет обновляются. Затем список/поиск/отмена и UI. Не создавать все возможные attendance/analytics interfaces на будущее.

- Добавь минимальный domain port (например AttendanceRepository) для согласованного чтения summary/участников, refresh/страниц и owner cancellation; имена выбрать по проектным соглашениям. Typed success/errors, независимость от HTTP/DTO/storage. Actor не принимается из UI; время через существующие event/auth Clock.
- Реализация использует **тот же** FakeProductState/Mutex/IO/storage. Не второй fake, не собственные копии tickets/checkIns в dashboard и не независимые seed counters. Новый slice вычисляет проекции из сохранённых записей; мутации используют общие бизнес-правила.
- Доступ owner-only на каждом чтении, странице, refresh и мутации. Participant/volunteer того же E не получают dashboard/PII; owner A не получает B. Route guard дополняет repository, не заменяет его. При утрате session/access немедленно очистить данные/confirmation и закрыть недоступный экран по текущей host policy; старый snapshot не держать на экране после denied.
- Summary одного снимка: `registered = ACTIVE + USED`, `checkedIn = USED`, `notCheckedIn = ACTIVE`; Cancelled не входят. Remaining=null для unlimited, иначе capacity−registered. Проценты без деления на ноль. Поиск/фильтр/страница **не меняют** totals. Для текущего события показывать «Ожидаются/ещё не пришли», после завершения — «Не пришли»; startsAt само не завершает событие.
- Для legacy/debug USED без first record учесть билет в checkedIn, но не выдумывать checkedAt/checker. Счётчик волонтёра «проверено N» — число настоящих первых CheckInRecord этого проверявшего на E, не число попыток/ошибок. Он может быть меньше общей USED-явки при legacy fixtures; это ожидаемое различие, не повод создавать историю.

### 2. Список, поиск и страницы

- Строка содержит стабильные registration/ticket ID для действий, имя, email и displayNumber, статус и при наличии первый check-in time/checker. Не передавать QR/manual credentials в list DTO, state, поиск или лог. Не показывать ответы анкеты/телефон, если конкретный экран их не требует; будущий экспорт не повод выводить лишние поля.
- Поиск по имени и displayNumber, без чувствительности к регистру, с trim; не по QR/manual. Изменение запроса сбрасывает страницу и отменяет устаревшую загрузку. Старый ответ/late finally не подменяет новую выдачу и не снимает её busy.
- Стабильная сортировка с tie-breaker ID и ограниченные страницы. Предложение для demo: по времени регистрации DESC + ID, используя существующий `consentAcceptedAt` только как документированный текущий timestamp регистрации; не выдумывать отсутствующие события времени. Новый persisted field вводить только при реальной необходимости и с миграцией.
- Выбери явную семантику paging: snapshot/revision-bound token или эквивалент. При мутации общего store нельзя смешивать старые страницы с новыми строками, терять/дублировать ID. Допустимо сбрасывать список на первую страницу по изменению relevant revision с понятным состоянием. Изменение UI-фильтра не сбрасывает серверные totals и не меняет записи.
- Cancelled сохраняются в данных/истории; текущий demo default для списка — все статусы, с ясной подписью счётчика участников. Если UI требует фильтры, не превращать статус в отдельную глобальную роль и не расширять произвольно макет. Число результатов поиска отделить от общего registered.
- Пустое событие и отсутствие результатов поиска — разные состояния. Растущие списки — LazyColumn/стабильные keys, никаких неограниченных layout-списков.

### 3. Owner cancellation и согласованность

- Только владелец выбранного E отменяет участника E. ACTIVE → CANCELLED, место освобождается один раз; повтор CANCELLED безопасен; USED не отменяется. Вложенный ID чужой регистрации не обходит проверку eventId. Личный билет и dashboard наблюдают одну запись.
- Не вызывай cancelOwnTicket от лица владельца для чужого билета и не подменяй пользователя. Общую логику изменения состояния выделить минимально, сохранив разные guards owner/self; не дублировать расходящиеся правила.
- Финальная проверка status/access под общим Mutex: если другой check-in уже сделал USED, отмена получает typed Used, не отменяет пройденный билет. Failure сохранения не публикует ложную отмену/counters. Logout/expiry/generation и отмена ожидающей операции не меняют чужую новую сессию.
- Confirmation принадлежит конкретной записи; Network/Timeout/Storage видны **внутри Dialog**, кнопка «Повторить» повторяет отмену того же ID. Не повторять закрытый P2 T07 с ошибкой под модальным окном. Busy блокирует повтор/закрытие по принятой политике. Успех очищает confirmation и обновляет общий store; denied очищает PII.
- Не менять вопросы/ответы, не снимать questionsLocked после отмены последнего участника. Schema 4 сохраняется, если новых persistent данных не понадобилось. Любое расширение codec сопровождается чтением всех прежних версий и сохранением данных всех writers; не повышать схему ради вычисляемых totals.

### 4. MVVM, навигация и freshness

- DashboardKey(eventId, entryId) и entry-owned Hilt ViewModel/UiState. Screen stateless, VM не знает fake/DTO/NavController. В SavedStateHandle максимум безопасный query/filter/scroll intent, не список участников или credentials; после восстановления авторизация и данные проверяются заново.
- MyEvents владельца → Dashboard; Dashboard → существующие Volunteers/Scanner → Back возвращает Dashboard и выбранное E в том же табе. Сохранить исправление `555a2a0`: внутренний переход не переключает принудительно на Tickets. Не копировать экран сканера и не добавлять результат scan отдельной растущей entry.
- Скрытый dashboard не держит активных UI-запросов/тяжёлых subscriptions; foreground/current возобновляет чтение. Camera lifecycle уже реализован в T07: возвращение из Scanner освобождает её, не ломает hidden-tab/session cleanup.
- Fake обновляет observed данные из store сразу. Показать время последнего успешного обновления и отдельную ошибку refresh со старыми данными, если доступ ещё есть. Явный retry повторяет чтение. Clock/now не брать напрямую в composable.
- Не добавлять настоящий polling 5 секунд/SSE ради demo: это будущее remote решение. В UI/отчёте честно указать локальное обновление, не обещать синхронизацию двух устройств без backend.
- Добавить checkedInCount в существующий volunteer read model и список по общим checkIns, если его ещё нет. Revoke не стирает first records; повторная выдача права сохраняет исторический счётчик. Владелец без self-grant сканирует как раньше; не создавать grant лишь для строки статистики.

## Проверки

Автоматизируй предметные риски, а не копии реализации:

1. Owner/volunteer/participant/guest, owner другого E, forged route и чужая page/registration: закрытые данные и команды защищены.
2. Guest/auth submit → одинаковые totals; ACTIVE→USED обновляет ticket/dashboard и счётчик конкретного проверявшего; AlreadyUsed/Invalid/ошибка ничего не увеличивают. Legacy Used не создаёт поддельную запись.
3. Отмена owner/self освобождает одно место, повтор не освобождает второе; USED запрещён, check-in/cancel race согласован, schema lock сохраняется, отказ записи не публикует успех.
4. Поиск/страницы не меняют totals; стабильные IDs, нет дублей/пропусков при смене revision; поздний ответ старого query и finally отмены не подменяют новые состояния.
5. Ошибка внутри confirmation и явный retry того же участника; refresh error/freshness, logout/expiry/hidden tab/возврат и очистка PII.
6. Небольшой device smoke owner→dashboard→scanner/manual→Back→обновлённая явка, поиск/отмена/модальная ошибка, Volunteers и исходный родитель. Ручную физическую камеру не заменять controlled-frame тестом.

Используй существующий Gradle wrapper/JBR 21 и зафиксированные зависимости. Запусти релевантные domain/fake/app/platform JVM suites, assemble app/test APK, lint, verifyDemoIsolation; не запускай параллельные Gradle builds в общей папке. При невозможности device-прогона явно записать причину, не подменять его JVM-проверкой.
