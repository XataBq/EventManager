## Объём

### 1. Контракты, права и сохранение — итерация T02

- EventRepository сейчас умеет читать публичное E и refresh. Добавь только нужные порты/модели: наблюдение общего списка своих E/черновиков, чтение для редактирования, saveDraft, publish/updateEvent, closeRegistration и finishEvent. Actor берётся внутри репозитория из подтверждённой сессии; ownerId из UI не доказывает право управления.
- Отдели **неполный черновик** от валидного опубликованного Event. Сейчас Event требует корректные Instant/venue/форму; не ослабляй инварианты и не подставляй фиктивные даты, чтобы сохранить незаполненную форму. Черновик имеет стабильный draftId и отдельную валидацию публикации.
- Все операции используют общий store с registrations/tickets/auth/grants, единый Mutex и существующий IO-путь. Typed outcomes: validation, conflict/stale form, unauthenticated/forbidden/not found, network/timeout/storage. UI выбирает локализованный текст из resources.
- Любой вошедший подтверждённый аккаунт может создать своё E; owner/grant/participation независимы. Волонтёр не получает редактор/список участников/экспорт. Прямой маршрут к чужому editor и команда repository проверяются независимо. Не вводи User.role.
- Доведи versioned snapshot до нужной схемы: drafts, опубликованные E/новые поля, стабильные IDs и состояние блокировки анкеты. Читай текущую server schema 2 и прежнюю auth schema 1 без потери аккаунтов/proofs/challenges/билетов/ответов; migration/reset явно задокументируй и протестируй. Не удаляй пользовательские demo-данные при обычном запуске/ошибке чтения.
- Storage failure не публикует ложный успех/ссылку/изменение E. Сессия и незавершённая регистрационная анкета по-прежнему не persist; постоянного guest cache нет. Сохранённый draft редактора и guest регистрационная анкета — разные сущности с разной политикой.

### 2. Один MyEvents

- Замени временный корневой раздел «Мероприятия» общим MyEvents: **Организую / Волонтёр / Черновики**, loading/error/retry/empty, выбор вкладки и список. Данные из одного store по действующей сессии, не три независимых demo-репозитория.
- «Организую» — владение, «Волонтёр» — действующий grant. Один E может входить в обе выборки. Отзыв grant убирает только эту связь; собственный билет остаётся. Никакого глобального переключателя роли и копий списка по ролям.
- Черновик виден только владельцу и открывает тот же редактор; создание — очевидное действие раздела. Опубликованные/завершённые E отображаются с корректными статусами по принятым правилам, без новой продуктовой сущности «архив».
- Dashboard/Volunteers/Scanner относятся к T07/T08: не реализуй их заранее и не делай фиктивные действия. Где макет ведёт туда, дай доступное действие текущего этапа (публичная страница/редактор владельца) либо честно обозначь ещё недоступное. Не показывай toast об успешном управлении, которого нет.

### 3. Редактор create/edit

- Одна форма без «Шаг 1 из 2», оплаты/платного переключателя. Основные поля: название, начало, место, лимит; необязательное окончание по B05. Поля/обязательность сверяй с источниками. Published E доступно публично по ссылке; доступность страницы и приём регистраций — разные состояния, сложную приватность/платные режимы не вводи.
- No limit отдельно от 0. Publish требует валидных обязательных полей, даты/окончания, timezone и анкеты. Общий capacity нельзя установить ниже числа действующих регистраций, включая Used, но не Cancelled. Серверное распределение последних мест не моделируй.
- Политика редактирования уже начавшегося/завершённого E и необязательных полей централизована: следуй согласованным правилам; недоопределённые технические defaults обозначь обратимыми и не выдавай за API. Не разрешай менять даты так, чтобы случайно вновь открыть завершённое E.
- Optional description/program не превращай в отдельный rich-text редактор: Q12 не согласовывает такой объём. Существующие description/sections и другие поля при редактировании сохраняй без потери, даже если их редактирование не входит в UI этой итерации.
- Кнопка «Сохранить черновик» сохраняет неполные данные надёжно; повторное открытие после нового процесса восстанавливает сохранённый draft. Несохранённые изменения при Back обрабатывай явным сохранить/выйти без сохранения/остаться; не сообщай «сохранено» до ответа. Если выбираешь autosave, отдельно обозначь состояния/ошибки и докажи, что старое завершение не затирает новую правку. Минимальный вариант — явное сохранение.
- Невалидная публикация оставляет данные редактируемыми и показывает ошибки полей; двойное нажатие не создаёт второй E. После подтверждённого успеха result/navigation потребляются один раз, повтор композиции не публикует заново. Запрос старой entry/сессии не обновляет новую.
- Даты из UI конвертируются с выбранной/отображённой timezone события; не парси локальную дату по случайной зоне устройства. Event Clock и auth Clock уже разделены; сценарии начала/окончания детерминированы.

### 4. Вопросы и formVersion

- Renderer/модели T05 переиспользуются. Редактор вопроса поддерживает text, checkbox, single-choice; стабильные IDs вопроса/варианта, required, порядок, добавление/удаление/изменение до первой регистрации. Для single-choice валидируй варианты; не пересоздавай все IDs при сохранении/перестановке.
- После **первой успешной регистрации**, в том числе гостевой без подтверждения email, вопросы/варианты/порядок/required фиксируются в MVP. Не жди check-in. Отмена всех билетов не снимает блокировку. В UI объясни причину; data-слой повторно проверяет запрет, поэтому устаревший открытый editor не обходит его.
- formVersion меняется при изменении схемы вопросов по одной политике; правка названия/места не должна без причины делать анкету устаревшей. Старые Registration.answers и их formVersion сохраняются. Устаревший редактор/публичная форма получает явный конфликт/StaleForm, а не молчаливое затирание новых данных.
- Факт первой регистрации должен переживать restart/migration. Используй существующую историю регистраций либо небольшой явный флаг, без несуществующих backend-обещаний. Редактор не имеет права переписывать ответы зарегистрированных участников.

### 5. Обложка

- Мобильный макет: PNG/JPG до 5 МБ, отображение 16:9. Используй системный picker, минимальные разрешения, обработку отказа/отмены/неверного файла/превышения размера. Не добавляй широкое разрешение на все фотографии или полноценный crop editor без нужды.
- Сохранённый draft/published E не должен терять обложку после смерти процесса/утраты временного URI grant. Выбери небольшой platform/demo adapter: устойчивый доступ либо управляемая копия, в domain — безопасный descriptor/reference, не Context/Bitmap/сырой Android API.
- Не доверяй одному расширению файла; не декодируй огромный оригинал в main. Не клади image bytes в route/SavedStateHandle/server snapshot. Очищай только принадлежащие приложению ненужные копии, сохраняя используемые. Публичный EventDetails T05 должен показать опубликованную обложку или fallback.
- Если обязательность обложки источниками не задана, явно используй обратимый optional default и fallback, не вводи новый блокирующий продуктовый вопрос.

### 6. Публикация и управление E

- Draft → publish → O03 с реальным eventId и действующей demo-ссылкой `eventpass-demo://demo/e/{eventId}`. Скопировать — настоящий Clipboard, поделиться — Android Sharesheet; cancel системного действия не является ошибкой публикации. Реальный домен/assetlinks/сервер не требуются.
- Ссылка cold/warm открывает существующий общий EventDetails T05 и именно сохранённую анкету. Частный draft не становится публичным до успешной публикации; прямое открытие чужого draft не раскрывает поля.
- Закрытие регистрации владельцем не скрывает описание и не аннулирует билеты. После startsAt новых регистраций нет. Manual finish либо endsAt переводят отображение/доступность в завершённое состояние; startsAt сам не равен Finished. Используй общие policies/Clock, а не независимые условия в каждом экране.
- Правки опубликованного E согласованно обновляют EventDetails/MyEvents и данные билета по принятой модели. Если TicketSnapshot сохраняет прежние title/venue/date, определи единое поведение отображения и проверь его; не меняй QR token/статус/принадлежность при обычной правке E. Не мигрируй билеты молча и не скрывай расхождение между экранами.

## Архитектура и проверки

Route получает Hilt ViewModel и lifecycle-aware UiState; Screen — state/callbacks, без repository/fake/navigation API. Сложную переиспользуемую координацию можно выделить, но BaseViewModel/reducer framework/новые модули и будущие порты не нужны. Сначала докажи saveDraft → restart → edit → publish → EventDetails на одном срезе, затем расширь. Автоматизируй инварианты, не каждый цвет/отступ:

| Сценарий | Требуемое доказательство |
|---|---|
| Пустой/неполный draft | Сохраняется и восстанавливается; publish отклоняется с ошибками |
| Чужой E/черновик/guest/expiry | Repository и навигация не дают управлять/увидеть чужие закрытые данные |
| Формы | IDs/порядок/required/варианты корректны, formVersion и StaleForm согласованы |
| Первая регистрация | Guest submit фиксирует вопросы; последующая правка отклоняется даже при stale editor, отмене всех и restart |
| Лимит/время | Capacity ниже действующих нельзя; unlimited/0 различаются; startsAt закрывает регистрацию, endsAt/manual finish завершают E |
| Persistence/migration/ошибка | V1/V2 читаются, draft/E и прежние accounts/tickets сохраняются; failure не выдаёт ложную публикацию |
| Состояние мутации | Двойной tap, late result/finally, Back/logout/новая entry не создают дубль и не меняют чужое состояние |
| Изображение/ссылка | Сохранённая обложка доступна после нового процесса, picker cancel безопасен; ссылка ведёт в нужное E |
| Общий store | Publish/edit/close/finish видны в списке и публичном E; guest receipt/tickets/session isolation не регрессируют |
