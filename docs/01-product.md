# Контекст и продуктовые правила

Статус: текущие целевые правила изменены прямым выбором пользователя 13 ноября. Каноническое задание backend — [32](32-backend-final-requirements.md). Server /api, autoaccount, immediate session, reset-link и остальные принятые defaults заменяют противоположные ранние B/Q-правила. Фактический Android demo ещё не адаптирован; его приёмки не означают выполнение новых сценариев.

## Продукт и границы MVP

EventPass — регистрация на мероприятия по ссылке, получение QR-билета, проверка прохода и учёт явки. Разрабатывается нативное Android-приложение; web и backend не входят в текущий этап.

В MVP: аккаунт (регистрация, подтверждение email, вход, восстановление, профиль, выход, удаление); публичная страница; гостевая и авторизованная регистрация на мероприятие; анкета организатора; билеты, полноэкранный QR, PDF и письмо; создание, черновики, редактирование и публикация мероприятия; лимит мест; выдача/отзыв прав; сканер и ручной ввод; дашборд, поиск участников, отмена регистрации, экспорт.

Исключены: каталог/поиск мероприятий, расширенная аналитика, платежи, Apple Wallet, отзывы, голосования, список ожидания, отдельное подтверждение участия, desktop-UI, архив. Поиск участников дашборда остаётся в MVP. «Реальное время» дашборда остаётся в MVP и не означает аналитику блока 05.

## Один аккаунт и независимые связи

- Гость — отсутствие сессии, а не роль в базе.
- Участник мероприятия — есть регистрация/билет на это мероприятие.
- Организатор — владелец конкретного мероприятия.
- Волонтёр — пользователь с действующим разрешением на сканирование конкретного мероприятия.
- Регистрация аккаунта без выбора типа; создание мероприятия доступно любому вошедшему пользователю.
- Владелец и волонтёр используют один сканер. Волонтёр не получает список участников, экспорт, настройки и управление правами.
- Владение A и право сканирования B не дают прав на C. Наличие билета на B само по себе не разрешает сканировать B.
- Пересечение связей внутри одного мероприятия разрешено для текущего demo/MVP по Q02. Владелец/волонтёр не получает билет автоматически, но может оформить обычную регистрацию; ограничения будущего API задаются общей политикой.

## Гость и подтверждение email

Гостевой submit создаёт аккаунт без пароля, билет и письмо с setup-ссылкой; QR выдаётся сразу и занимает место. AccountCreated/accessToken используются как на backend. Guest ticket capability не является session bearer. Compact receipt текущего flow сохраняет QR при возврате/recreation; постоянный guest cache Android не требуется. Доступ по защищённой ссылке письма остаётся серверным.

Signup сразу выдаёт Session, login разрешён до подтверждения email. Подтверждение/setup/reset — через одноразовую серверную ссылку на 24 часа; установка/смена пароля одновременно подтверждает email. Кодовый reset и verified-only gate больше не требуются. Один opaque bearer на 30 дней, без refresh и обязательного expiresAt; после истечения повторный login. Реальные token storage и auth links адаптируются отдельно.

Существующий email гостя — EMAIL_TAKEN и переход во вход по backend. Ответы анкеты и автоматический submit после login на Android по-прежнему не добавляются: прямое правило B04 не отменено этим выбором. Серверный web pendingRegistration не копируем автоматически. Тексты UI — Android resources, исходы по машинным codes.

## Мероприятие и анкета

Public E открывается по slug, внутренние команды идут по id. Поля/DTO/server limits принимаем за основу. Обложка optional JPEG/PNG до 5 МиБ, отображение 16:9; описание/программа plain text. Загрузка/привязка cover и сохранение sections — необходимые доработки BK04/BK05. MAX/payment/каталог не добавляем.

Неполный draft сохраняется с незаполненными полями/вопросами; publish проверяет полноценное E. У опубликованного события capacity только положительный, без unlimited/null и общего лимита 0. Остаток 0 означает отсутствие мест. Последнее место распределяет сервер.

Регистрация разрешена в published/live при наличии мест. StartsAt не закрывает заявки. Отдельного действия закрытия регистрации не будет. Finished — по ручной команде owner или по effectiveEndsAt: явно заданный endsAt, иначе startsAt+4 часа. По умолчанию событие заканчивается через четыре часа после начала. Завершённое вручную E не оживает от PATCH даты.

Вопросы и варианты можно добавлять/изменять/удалять после регистраций; старые answers/labels сохраняются снимком, без переинтерпретации новым типом. Вечный questionsLocked и обязательный formVersion из прежнего предложения не требуются. Принимаем server question types/минимум options, дополнительно нужен boolean checkbox (BK06). Имя Unicode, phone optional в UI; мелкие server field/default различия адаптируются, отдельный policy/config framework не обязателен. Вопросы «Формат участия»/«Вуз» не являются глобальными ролями.

## Билеты и отмены

Базовые состояния ACTIVE→USED при первом проходе и ACTIVE→CANCELLED при отмене. Участник отменяет собственный ACTIVE, owner E — ACTIVE участника E; USED отменять нельзя. Повтор отмены освобождает место только один раз. После отмены новая регистрация возможна по server lifecycle/capacity со свежим ticket/credentials.

Текущие server current/history grouping и разрешённые статусы PDF принимаем за основу, Android адаптирует отображение. QR содержит opaque qrToken без PII; ручной ввод — ticket.code EVT-xxxxxx. Отдельный 12-char ManualCode в реальном API не используется. Пример макета не является рабочим credential.

PDF скачивается напрямую с проверкой доступа, без DocumentJob API. XLSX всех участников/исторических ответов — доработка BK07; CSV сохраняется дополнительно. Новую функцию повторной отправки ticket email не реализуем по последнему решению пользователя. Первоначальные письма и существующие повторные auth-ссылки сохраняются. Экспорт не создаёт новый ticket и место. Источник snapshot и semantic errors скрыты за ports.

## Проверка прохода

Порядок будущей серверной проверки и её fake-эквивалента:

1. Действующая сессия и право сканировать выбранное мероприятие.
2. Токен найден, билет принадлежит этому мероприятию.
3. Регистрация не отменена.
4. Билет ещё не использован.
5. Атомарно пометить Used, записать время и проверившего, обновить наблюдаемые данные.

Три бизнес-результата: разрешён / уже использован / недействителен. При повторе показывать первый проход и проверившего. Ошибка сети не означает «Билет недействителен». Отозванные права → закрыть сканер, перейти в «Мои мероприятия». Автоматического разрешения прохода офлайн в MVP нет. Повторный проход после Used не засчитывается.

## Организатор и профиль

«Мои мероприятия» общие: Организую / Волонтёр / Черновики. Сканер открывается из мероприятия, отдельного глобального таба сканера нет. Прошедшие волонтёрские мероприятия скрыты, прошедшие собственные доступны свёрнутым списком.

Дашборд: зарегистрировано, пришли, ещё не пришли, поиск по имени/номеру, статусы и время. Экспорт включает всех участников и ответы, а не только результаты текущего поиска. Отмена участника доступна владельцу через меню строки.

Профиль/limits/PATCH, включая поддерживаемую сервером смену email, принимаем как server defaults. Копирование publicId, notifications и logout сохраняются. **Q10 согласован 13 ноября:** DELETE /me без повторного пароля/preview, с текущим каскадом собственных E и чужих tickets на них, своих tickets/grants/scans. Android показывает явное подтверждение последствий, после успеха очищает session/private UI. Продуктовое решение не является уже выполненной Android-операцией.

## Общие состояния, отсутствующие в макетах

На каждом источнике данных: загрузка, пустой результат, ошибка и повтор, отсутствие сети; для мутаций — отправка и защита от повторного нажатия. Отдельно: истёкшая сессия, утраченные права, камера запрещена, подтверждение email, восстановление/задание пароля, полноэкранный QR, подтверждения отмены/удаления/отзыва прав, редактор вопроса, список черновиков и истории.

Эти состояния не расширяют продукт до MAX: они необходимы для завершения заявленных MVP-сценариев.
