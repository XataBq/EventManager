## Продукт и границы MVP

EventPass — регистрация на мероприятия по ссылке, получение QR-билета, проверка прохода и учёт явки. Разрабатывается нативное Android-приложение; web и backend не входят в текущий этап.

В MVP: аккаунт (регистрация, подтверждение email, вход, восстановление, профиль, выход, удаление); публичная страница; гостевая и авторизованная регистрация на мероприятие; анкета организатора; билеты, полноэкранный QR, PDF и письмо; создание, черновики, редактирование и публикация мероприятия; лимит мест; выдача/отзыв прав; сканер и ручной ввод; дашборд, поиск участников, отмена регистрации, экспорт.

Исключены: каталог/поиск мероприятий, расширенная аналитика, платежи, Apple Wallet, отзывы, голосования, список ожидания, отдельное подтверждение участия, desktop-UI, архив. Поиск участников дашборда остаётся в MVP. «Реальное время» дашборда остаётся в MVP и не означает аналитику блока 05.

## Один аккаунт и независимые связи

- Гость — отсутствие сессии, а не роль в базе.
- Участник мероприятия — есть регистрация/билет на это мероприятие.
- Организатор — владелец конкретного мероприятия.
- Волонтёр — пользователь с действующим разрешением на сканирование конкретного мероприятия.
- Регистрация аккаунта без выбора типа; создание мероприятия доступно любому вошедшему пользователю.
- Владелец и волонтёр используют один сканер. Волонтёр не получает список участников, экспорт, настройки и управление правами.
- Владение A и право сканирования B не дают прав на C. Наличие билета на B само по себе не разрешает сканировать B.
- Пересечение связей внутри одного мероприятия разрешено для текущего demo/MVP по Q02. Владелец/волонтёр не получает билет автоматически, но может оформить обычную регистрацию; ограничения будущего API задаются общей политикой.

## Гость и подтверждение email

Гость отправляет анкету → backend возвращает QR-билет приложению и отправляет билет на указанную почту. Аккаунт автоматически не создаётся. В Android показываем QR и сообщение о письме; компактные данные билета сохраняем в saved instance state текущего flow для возврата к странице. После явного закрытия flow гостевой доступ не сохраняется: открыть билет можно из письма либо через самостоятельную регистрацию аккаунта, подтверждение email и ручной вход. Кабинет показывает все билеты на этот email; привязку выполняет backend.

Существующая почта: допустим ответ «аккаунт существует» и переход во вход. Ответы формы не сохраняются, регистрация после входа автоматически не завершается. Возвращаемся на исходное мероприятие; анкету заполняют и отправляют заново. Это рабочий вариант ветки existing-email на основании B04, до реальных ответов API.

Гостевой билет действует и занимает место без подтверждения почты. Подтверждение аккаунта не выполняет автоматический вход: после него нужен обычный вход. Восстановление пароля: email → код из письма → новый пароль; отдельное предварительное подтверждение почты не требуется. Тексты ошибок «Неверный пароль» и «Необходимо подтвердить email» находятся в Android string resources. Настоящая доставка писем — задача backend; demo показывает имитацию результата.

## Мероприятие и анкета

Основные поля: название, начало, место, лимит; mobile-макет также содержит обложку (16:9, PNG/JPG до 5 МБ) и доступ по ссылке. Анкета содержит вопросы с ID, типом и порядком: текст, чекбокс, выбор одного варианта. Базовые данные гостя вводятся полями; для вошедшего берутся из профиля. «Формат участия», «Вуз/факультет» — примеры пользовательских вопросов, а не системные роли или enum.

Сохранение черновика допускает неполные поля; публикация проверяет обязательные поля и согласованность даты/лимита/вариантов вопросов. Платные мероприятия скрыть. «Шаг 1 из 2» убрать: в MVP одна форма. По принятому Q08 вопросы можно менять до первой регистрации, после — вопросы и варианты фиксируются. Версия анкеты сохраняется вместе с ответами.

По B06 телефон optional и в профиле, и в исходной политике регистрации; если введён — российский номер. Политику можно централизованно переключать Required/Optional/Hidden без удаления прежних значений. Имя допускается на любом языке, без требования ровно двух слов и ограничений кириллицей/латиницей; проверяем непустое значение и базовую корректность. Ответы анкеты при уходе в другой сценарий не сохраняем по B04.

По Q12 опубликованное событие публично доступно по ссылке. Закрытие регистрации не скрывает автоматически описание и не аннулирует существующие билеты. Состояния страницы/регистрации приходят из общего слоя данных, позднее — API.

Публичная страница: открытая регистрация / нет мест / закрыто / мероприятие прошло / не найдено. После начала регистрация недоступна, даже если событие ещё идёт. Завершение — по действию владельца или по заданному времени окончания. Отсутствие лимита означает неограниченную регистрацию; 0 доступных мест — запрет новых заявок. Последнее место распределяет сервер; Android только отображает успех/CapacityReached, без моделирования серверной гонки. Вошедшему с существующим билетом показываем «Открыть билет».

## Билеты и отмены

Базовые состояния: Active → Used после первого успешного прохода; Active → Cancelled после отмены. Used означает, что по билету уже прошли, а не что мероприятие закончилось. По принятому B08 Used отменять нельзя; новая регистрация после Cancelled получает новый билет/токен при открытой регистрации и наличии мест. «Посещено» и «Не пришёл» — представление истории, а не новые состояния токена. Завершение события определяется по B05, отдельно от времени начала.

Выбранный билет и список находятся на одном экране «Мои билеты». Нажатие «Открыть билет» меняет выбор, отдельный экран детализации из архива не создаётся. История не показывает QR. Отмена активной регистрации требует подтверждения, аннулирует билет и освобождает место один раз.

QR содержит только непрозрачный уникальный токен; печатный номер билета не обязан быть этим токеном. Никаких ФИО, email, прав пользователя или JSON-профиля внутри QR. Пример QR из макета не использовать как рабочий код.

## Проверка прохода

Порядок будущей серверной проверки и её fake-эквивалента:

1. Действующая сессия и право сканировать выбранное мероприятие.
2. Токен найден, билет принадлежит этому мероприятию.
3. Регистрация не отменена.
4. Билет ещё не использован.
5. Атомарно пометить Used, записать время и проверившего, обновить наблюдаемые данные.

Три бизнес-результата: разрешён / уже использован / недействителен. При повторе показывать первый проход и проверившего. Ошибка сети не означает «Билет недействителен». Отозванные права → закрыть сканер, перейти в «Мои мероприятия». Автоматического разрешения прохода офлайн в MVP нет. Повторный проход после Used не засчитывается.

## Организатор и профиль

«Мои мероприятия» общие: Организую / Волонтёр / Черновики. Сканер открывается из мероприятия, отдельного глобального таба сканера нет. Прошедшие волонтёрские мероприятия скрыты, прошедшие собственные доступны свёрнутым списком.

Дашборд: зарегистрировано, пришли, ещё не пришли, поиск по имени/номеру, статусы и время. Экспорт включает всех участников и ответы, а не только результаты текущего поиска. Отмена участника доступна владельцу через меню строки.

Профиль: сохранение данных, копирование ID, настройка email-уведомлений, выход, удаление с повторной проверкой пароля. По заметке удаление затрагивает также созданные мероприятия; это обязательно явно показать в подтверждении и согласовать с backend (Q10).

## Общие состояния, отсутствующие в макетах

На каждом источнике данных: загрузка, пустой результат, ошибка и повтор, отсутствие сети; для мутаций — отправка и защита от повторного нажатия. Отдельно: истёкшая сессия, утраченные права, камера запрещена, подтверждение email, восстановление/задание пароля, полноэкранный QR, подтверждения отмены/удаления/отзыва прав, редактор вопроса, список черновиков и истории.

Эти состояния не расширяют продукт до MAX: они необходимы для завершения заявленных MVP-сценариев.
