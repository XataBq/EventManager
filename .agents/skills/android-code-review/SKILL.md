# Android Code Review

Проводить ревью только по явному запросу пользователя или вызову `$android-code-review`. Создание или настройка этого скилла не означает запрос на ревью. Не запускать полное ревью автоматически при реализации, исправлении ошибок, рефакторинге или написании тестов.

## Границы

- Ревью доступно только для чтения исходников приложения. Не исправлять находки без отдельного разрешения пользователя. Разрешённый результат — `CODE_REVIEW.md` в корне проекта.
- Сохранять посторонние изменения. Не менять статусы задач, решения, зависимости и конфигурацию ради ревью.
- Проверки запускать соразмерно области ревью, через существующие инструменты проекта. Не запускать команды с исправлением файлов. Не отмечать человеческую UI-приёмку пройденной.

## Порядок работы

1. Прочитать корневой `AGENTS.md`, `README.md`, `docs/08-decisions.md` и относящуюся к изменению задачу из `docs/06-delivery-plan.md`. По `docs/00-documentation-map.md` выбрать нужные документы; для кода учитывать `docs/14-engineering-rules.md`. Продуктовые ответы `docs/12-backend-answers-2026-10-27.md` имеют приоритет над ранними сценариями Figma.
2. Установить область ревью из запроса: файлы, задача, commit или diff. Если Git доступен, проверить status и соответствующий diff, затем прочитать изменённый код и его вызывающие места. Без указанной области использовать незакоммиченные изменения и явно назвать это допущение. Если Git или diff отсутствуют, не придумывать базу сравнения: проверить явно указанные файлы либо уточнить область. Если кода ещё нет, отразить это ограничение.
3. Искать конкретные ошибки и регрессии, оценивая наблюдаемое поведение: сценарии и доступ по eventId; границы MVVM/DI/repository; состояние, recreation и process death; отмену корутин и повторные операции; обработку ошибок; навигацию; безопасность токенов и персональных данных; соответствие контрактам и достаточность тестов. Читать связанный код, чтобы проверить каждое предположение.
4. Учитывать специфику EventPass: один аккаунт без глобального User.role; общие EventDetails/MyEvents/Scanner; fake только за repository ports через DI; гостевой QR в состоянии текущего flow без постоянного guest cache и автосоздания аккаунта; сервер распределяет места и подтверждает check-in. Не требовать реализации будущих этапов или неподтверждённого API.
5. Подтверждать находки точными файлами и строками, условием возникновения и последствием. Отличать дефект от предпочтения по стилю. Не выдавать неподтверждённую гипотезу за ошибку; существенные неизвестные вынести в вопросы. Версии и меняющиеся технические факты при необходимости сверять с актуальными первичными источниками.
6. Выполнить минимальные подходящие проверки, если среда позволяет, и записать точные команды и результаты. Отсутствие запуска не считать успешной проверкой.

## Отчёт

Сохранить отчёт на русском в `CODE_REVIEW.md`. Если там уже есть отчёт, сохранить предыдущие записи и добавить новую датированную запись, если пользователь не просил заменить файл.

Включить:

- Дату, область ревью и доступную идентификацию состояния: commit/diff/пути; при отсутствии Git — явное ограничение.
- Находки по убыванию серьёзности: P0 — критическая блокирующая проблема; P1 — серьёзная ошибка, исправить до поставки; P2 — обычный дефект; P3 — малозначимый дефект. Для каждой: краткий заголовок, файл и минимальный диапазон строк, условие/сценарий, последствие, доказательство и направление исправления без изменения кода.
- Вопросы и допущения отдельно от подтверждённых дефектов.
- Запущенные проверки с результатами, незапущенные проверки и ограничения, включая ожидающую ручную приёмку.

Если подтверждённых находок нет, прямо написать об этом и назвать пределы проверки; не объявлять весь проект безошибочным. В ответе пользователю кратко перечислить главные находки и дать ссылку на отчёт. Не создавать искусственные замечания ради количества.
